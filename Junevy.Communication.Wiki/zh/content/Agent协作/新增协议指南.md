# 新增协议指南（地址型设备协议包）

面向在本仓库实现新的地址型协议包（S7、FINS 等）的智能体。开工前先读 [[Agent协作/开发约定与验收基线]]（AGENTS.md 硬性约定）与 [[架构设计/Plc 地址型设备协议套件]]。参照实现有三个：`Junevy.Communication.Melsec`（字与位软元件、三种传输）、`Junevy.Communication.Siemens`（字节软元件、单一 TCP 传输、双数字地址、协商出的 PDU）、`Junevy.Communication.Omron`（字软元件 + 原生位写、单一 TCP 传输、握手取路由）；使用者与作者的完整说明见 [Skills/using-junevy-plc/SKILL.md](file://Skills/using-junevy-plc/SKILL.md)。

## 一、架构先行（AGENTS.md 第 2 节）

- 开工前设计架构，考虑扩展性、维护性与耦合性。协议包只依赖 Plc 与它所用的通道项目。
- 不修改 Core、Channels、Plc 的代码。需要改套件时，先说明套件缺口，再作为通用能力补进套件，并向用户提问。
- 发现更优的实现方式，或当前方式不符合设计规范，必须提问，并先检索是否有更好的方式。
- 不确定的功能先问，可扩展的功能先问是否扩展。

## 二、必须写与不需要写（设计 12.8，P4 定型）

| 必须写 | 套件已提供，不要重写 |
|---|---|
| 设备表与地址类型（`PlcAddressParser<TDevice, TAddress>`，设备实现 `IPlcDeviceDefinition`）；地址带两个数字时自写解析器（S7），但仍实现 `IPlcDeviceDefinition` | 连接、重连、心跳调度、超时 |
| 钩子（见下表的契约）；需要时覆写 `ValidateRange`（表示范围与点数上限） | 请求串行化、重试、拆包、类型化读写、字节序与字序转换 |
| 帧编解码（无通道依赖，放在 `Protocol/`）与流式分帧的声明（`Framing/`） | 流式分帧的实现（只声明长度字段或分隔符） |
| 通道组件声明与守卫（分帧、关联、初始化器、心跳探测）；需要协商时用 `IConnectionInitializer` + 会话快照 | 字节 / 字 / 位三种粒度到钩子的路由 |
| 协议的创建入口 `Create(IChannelConfig …)`（经 `PlcChannelBinding.CreateChannel`）、创建器、`AddX()` | TCP、UDP、串口的传输适配 |
| 设备替身与端到端测试 | 日志、注册表、工厂、模拟服务器（使用 Testing 的 `DeviceSimulator`） |

### 钩子契约（`PlcClientBase<TAddress>` 的类级 XML 注释同步保存这份表）

| 钩子 | 可见性 | 是否必须覆写 |
|---|---|---|
| `TryParseAddress` | `protected internal abstract` | 必须 |
| `GetMaxReadPoints(TAddress, PlcAccess)` / `GetMaxWritePoints` | `protected internal abstract` | 必须；返回值按 `access` 的单位计（`Words` 计字、`Bits` 计点、`Bytes` 计字节） |
| `BuildReadWordsRequest` / `ParseReadWordsResponse` / `BuildWriteWordsRequest` | `protected internal abstract` | 必须（类型化读写都走字路径） |
| `BuildWriteBitsRequest` / `ParseWriteResponse` | `protected internal abstract` | 必须 |
| `BuildReadBitsRequest` / `ParseReadBitsResponse` | `protected internal virtual`，默认抛 `InvalidOperationException` | 只有软元件表含位软元件的协议需要覆写 |
| `BuildReadBytesRequest` / `ParseReadBytesResponse` / `BuildWriteBytesRequest` | `protected internal virtual`，默认抛 `InvalidOperationException` | 含字节软元件（`PlcAddressUnit.Byte`）的协议必须覆写；`offset` 与 `count` 都按字节计 |
| `CanWriteBitsNatively(TAddress)` | `protected internal virtual`，默认 `address.Unit == PlcAddressUnit.Bit` | 字软元件能原生写位时覆写为 `true`（FINS）；位访问的绝对位置 = 编号 × 每单位点数 + 位号（无位号视为 0）+ 包内偏移 |
| `ValidateRange(TAddress, PlcAccess, int)` | `protected internal virtual`，默认成功 | 协议表示不了的请求在此返回 `InvalidRequest`（含地址字段越界） |

未覆写的 `virtual` 钩子抛出的异常由流水线收口为 `Unspecified` 并记 Error，所以"用不到的钩子"不需要写死代码，调用方仍得到结果而不是异常（P4-D5）。`Build*` 钩子返回 `void`，不能报告错误。

### 单位、字节访问与握手

- 三种单位（`Bit` / `Word` / `Byte`）决定读位与读字节的换算：字节软元件的位点 `p` 在第 `p / 8` 字节的第 `p % 8` 位（位 0 是最低位）；字与位软元件上的 `ReadByteAsync` 返回规范化布局的首字节（对端字序决定是哪一半）；字与位软元件的 `WriteBytesAsync` 要求偶数长度。带位号的地址一律被 `ReadBytesAsync` / `WriteBytesAsync` / `ParseAddress` 拒绝。
- 需要协商结果（S7 的 PDU 大小、FINS 的节点号）时：`ChannelComponents.Initializer` 挂 `IConnectionInitializer`，每次重连都重新执行；握手结果写进**不可变快照**，用 `Volatile` 整体替换引用，钩子读当前快照；不要把协商值塞进选项，也不要让钩子与初始化器各持一份可变状态。上限算术放在 internal 的会话类型里比放在钩子里更容易测试（计划 20.2 节 F5）。
- S7 与 FINS 都用 `CorrelationMode.Sequential`：握手帧没有关联键，`Keyed` 模式下初始化器的 `RequestAsync` 会被 `InvalidRequest` 拒绝；套件的操作锁本来就串行，字节流上的请求超时后通道会重建并重新握手。应答解码要自己校验回显（S7 的 PDU 引用号、FINS 的 SID 与命令码），不一致返回 `ProtocolViolation`（P4-D8）。
- 只走单一传输的协议，DI 配置不给传输开关（`S7ClientConfig` / `FinsClientConfig` 只有 `Tcp` 与 `Options`），置空 `Tcp` 时创建器抛 `ArgumentException`；`PlcDataFormat` 无可参构造函数，数据格式不能由 JSON 绑定。

## 四、测试约定

- **黄金向量是唯一的正确性来源**：帧编码与解码按手册示例逐字节核对，手册给出两个方向时双向测试。
- **设备替身只翻译，不重写协议**：替身把请求翻译成 `PlcMemory` 操作，应答可复用协议层的字段编码；目标 200 行以内。替身必须实现握手的应答（S7 的 COTP CR → CC → Setup Communication、FINS 的节点地址请求），否则客户端跳过协商也能连上，"快照没写入"这类缺陷测不出来。
- 按字节组织的存储（S7 的 DB 块、"块不存在"与"越过块尾"两种不同错误）用共享测试库的 `PlcByteMemory`，不要替身自带（**P4.6 已解决**）：`Define(area, block, length)` 建全 0 的块并返回存储、`Block(area, block)` 取出来预置与核对、`TryRead` / `TryWrite` 返回 `PlcByteAccess.Ok` / `NoSuchBlock` / `BeyondEnd`，写失败时块不变；把后两种翻译成协议自己的错误码。字粒度仍用 `PlcMemory`——**它没有被改成 `PlcByteMemory` 的视图**（原 F7 笔记里"改为其上的视图"这一半**没做**，理由见 [[测试/P4.6 测试基建整理（已完成）]]）。字软元件的原生位写要落在同一份字内存上（读-改-写覆盖字），不要另存一份位字典；FINS 的位在字内的字节布局属于协议本身（它是 `FinsSimulatorMemory` 那一侧的活），共享库只管字节。
- 等待统一用共享测试库：`Polling.WaitUntilAsync(() => …)` 轮询条件、`Arrival.WithinAsync(task, ms)` 等某个任务在时限内到达，不要再写 `Task.WhenAny` + `Task.Delay` 的竞态（**P4.6 已解决**）。帧测试的十六进制向量用 `HexVector.ToBytes(...)`。
- "发一帧、等一帧"的单测用 `ScriptedByteChannel`（`LastRequest` 是最近一次 `RequestAsync` 的帧，`SendAsync` 不改它）。
- **端到端矩阵**：每个传输 × 每种帧 × 每种编码；拆包（上限边界）；异常结束码；断开后重连再读取（并核对重新握手的证据）；静默设备加心跳进入 `Reconnecting`；有序列号的协议测迟到应答。
- **集合约定**：真实套接字或墙钟预算的测试类加 `[Collection(SocketTimingCollection.Name)]`，避免偶发失败。
- **等待用轮询**：`WaitUntilAsync` 类辅助，不用 `Thread.Sleep`。
- **`DuplexClientChannel` 的 `onOpened` 会被等待**：在回调中启动模拟器而不返回它的任务，否则连接挂起。
- **真实串口测试**（`SerialPairFact`）只在设置了 `JUNEVY_SERIAL_PAIR` 的机器上运行；执行者不运行，由审阅者运行。

## 七、SDK 协议适配（P6）

地址型协议包之外还有一类：**自己实现协议不划算，用现成 NuGet 又不能把 SDK 的类型漏给使用者**。P6.1 的 `Junevy.Communication.Mqtt` 是第一个样板，P6.2（OPC UA）是第二个，P6.3（FTP）照做。

### 1. 薄类型与依赖边界

- **公开 API 只能用本库与 BCL 的类型。** 给每个对外概念写一个本库的薄类型（`MqttMessage`、`MqttQos`、`MqttProtocolVersion`、`MqttConnectionState`…），SDK 类型只活在 `Sdk/` 目录。
- **SDK 只能出现在一个命名空间。** `Sdk/` 下的类型全部 `internal`；同名时用别名（`using SdkClient = MQTTnet;`）。实测撞名的至少有 `MqttClient`、`MqttClientOptions`、`MqttProtocolVersion`、`MqttUserProperty`。
- **映射只有一处。** "SDK 的异常或原因码 → `CommErrorKind`"集中在 `Sdk/XxxErrorMap` 一个类型里（Q38），并且**映射表的每一行都要有一条测试**。别处不得再写一份判断。
- **依赖**：适配包只引用 Core 和自己的 SDK，不引用 Channels / Tcp 等（P6-C6）。
- **只面向 net8.0**（P6-C1）：三个 SDK 的新版本都不再支持 net472。新包不受仓库其余部分的 net472 禁用清单约束，但其余约束（可空性、文档、常量日志模板）照旧。

### 2. 三条架构守卫（写一次，后面每包加一行）

`Tests/Junevy.Communication.Architecture.Tests/SdkAdapterArchitectureTests.cs`，只编译 net8.0（三个包都是 net8.0 单目标，net472 下连引用都建立不起来）：

1. **分层**：适配包只引用 Core。
2. **公开 API 不出现 SDK 类型**：反射遍历导出类型的基类、接口与公开 / 受保护的字段、属性、方法、事件、构造函数，展开数组 / 指针 / byref / 泛型实参后检查程序集名。**私有成员不检查**——`Sdk/` 里的内部类型用 SDK 类型是允许的。
3. **`Sdk` 命名空间以外不依赖 SDK**：用 NetArchTest 读 IL，因此方法体里的引用也算。

外加 `ArchitectureTests.SdkPrefixes` 的**程序集引用白名单**。新包要改四处，每处一行：
- `SdkAdapterArchitectureTests.Adapters`（三列：适配程序集、SDK 程序集名前缀、SDK 命名空间）——三条检查随之生效；
- `ArchitectureTests.SdkPrefixes`（白名单）；
- `ArchitectureTests.LayerTable`（放在 `#if NET8_0_OR_GREATER` 里，允许引用只有 Core）；
- `Architecture.Tests.csproj` 里只在 net8.0 生效的 `ProjectReference`。

> 每条新守卫都要先临时制造一次违规确认它会失败（负控），再撤掉。不做负控的守卫等于没写。

### 3. 不要重复实现协议里已有的校验

主题 / 过滤器合法性、MQTT 5 属性在 3.1.1 下是否受支持——都交给 SDK 自己的校验器，只把"抛异常"翻译成 `InvalidRequest`。**唯一例外**：实测发现 SDK 的 `MqttApplicationMessageValidator` 不认为 `MessageExpiryInterval` 是 5.0 only，而需求要求"3.1.1 上一项 MQTT 5 属性都不能带"，因此单独补了这一条判断，其余四项仍交给 SDK。

### 4. SDK 行为必须由测试钉住

薄适配层最大的风险是 **SDK 悄悄改了行为**。凡是适配代码依赖的 SDK 行为都要有一条直接验证它的测试。本期实测到的（完整记录见 `docs/superpowers/plans/2026-10-12-p61-mqtt.md` 第 18.2 节的 F1–F13，最值得记住的三条）：

- **失败通过异常还是返回值报告？** MQTTnet 的 CONNACK 是**返回值**（`MqttClientConnectResultCode`），连接被中止则是**异常**——两条路径都要收口，否则一个漏网。
- **异常类型里读不出原因。** 连接被中止（调用方取消 / 等待超时）抛的都是笼统的 `MqttCommunicationException`。因此每次操作由本包开一个 `TimeoutScope`，分类时**先看作用域再看异常类型**——与 WebApi 的 `HttpStatusClassifier` 同一做法。TLS 的认证异常同样被包在里面，要沿内层异常链找。
- **SDK 可能已经没有你以为的那个功能。** MQTTnet 5 的 `MqttClientOptions` 上**没有** `AutoReconnect`——客户端自动重连被 SDK 移除了。这反而是好事：重连完全归本包，不用防"两套重连打架"。

### 5. 测试替身：优先用 SDK 自带的

- MQTT 用 `MQTTnet.Server` 的进程内 Broker，FTP 因为没有像样的第三方服务器包才自写模拟服务器。
- 替身只包一层，让用例碰不到 SDK 的事件类型：`TestBroker` 把 SDK 的事件字段摊平成 `record ObservedConnect` / `ObservedSubscription`。
- **SDK 的测试服务器也有自己的坑**，照文档直觉写会直接写错（MQTTnet.Server）：
  - `WithDefaultEndpointPort(port)` **不会**启用默认端点（`IsEnabled` 仍是 `false`），`StartAsync()` 之后 `IsStarted` 为 `true` 但端口上没有监听；还要显式 `WithDefaultEndpoint()`。
  - 它不把实际绑定的端口写回选项对象，而且 `TlsEndpointOptions.Port` 默认 8883——要自己用临时 `TcpListener` 向操作系统要一个空闲端口。
  - `InterceptingInboundPacketAsync` **在 CONNECT 上不触发**，既不能记录 CONNECT 也不能延迟 CONNACK；改用 `ValidatingConnectionEventArgs`（它带 CONNECT 的全部字段，但不含遗嘱的 topic / 正文 / retain）。

### 6. 本期摩擦的结论

- 映射表放在**一个**内部类型里，第 15 节那种"逐行列表 + 逐行测试"的写法值得照抄。
- 状态机、重连策略、消息操作分三个内部类型，比塞进一个 `XxxClient` 好：生命周期与消息操作的**并发规则本来就不同**（前者走锁、后者可并发）。
- 重连这种"后台循环"不要抽成 Core 的通用 `RetryLoop`（同 P2-D3 的结论）：它带状态迁移和恢复订阅。
- **测试替身本身也会有竞态**：Broker 还活着时重连只有几十毫秒，`WaitUntilAsync(State == Connected)` 会**在状态变化之前就返回**。要先等一个确定性的外部证据（例如 Broker 看到的 CONNECT 计数增加），再等状态。
- **"一次性"的后台循环容易只跑一次**：句柄忘了在退出时清空，第二次触发就被"已经在跑"挡掉，状态永远停在中途。写任何 `TryStart` 都要配一条"连续触发两次"的用例。
- **验收时补充的三条**（2026-10-12）：
  - "停止"与"释放"要分开：应用的 `DisconnectAsync` 只结束当前这一轮重连，释放才永久停止。原实现在断开时把循环永久停掉，断开后又连上的客户端再掉线就永远停在 `Reconnecting`。用例要覆盖"断开 → 再连 → 意外断线"这条路径。
  - 恢复订阅时要区分"对方拒绝"与"链路出问题"：只有前者才把订阅移出表，后者让这一轮重连失败、再试。否则一次超时就会永久丢掉订阅。
  - 释放时不要释放仍可能被租约使用的锁（`SemaphoreSlim`）；释放之后的操作按约定返回结果，不要抛异常。释放还要先取消进行中的连接，再在锁内释放 SDK 客户端。

### 7. P6.2 的结论（OPC UA，2026-10-16）

**开工前先调研，不要照着上一代 SDK 的记忆写。** OPC UA 的 2.0 线在 2026-10 才发，公开资料极少；SDK 调研（F1–F29）在 `docs/superpowers/plans/2026-10-12-p62-opcua.md` 第 19.2 节，**仓库外**的临时 net8.0 控制台工程比读文档快得多。四条最值得记住的：

- **新 SDK 会换掉你熟悉的类型。** 2.0 把 API 里的 `object` 换成了 struct `Variant`，于是 `Guid` 变成 `Uuid`、`DateTime` 变成 `DateTimeUtc`（数组同理），`Variant.From<object>(42)` 直接编译不过。"把 SDK 类型包一层"的老办法不够用，要写两张按**精确类型**分派的映射表（而且必须精确相等：.NET 7 起 `sbyte[]` 在 `is byte[]` 下为真）。
- **SDK 可能在你等错误的时候阻塞。** `ManagedSessionBuilder.ConnectAsync` 没有超时参数，"端口没人监听""只开放加密端点""不允许匿名"三种情况都**一直阻塞到调用方令牌触发**，一个状态码都给不出来。超时、取消、释放打断连接三件事都得本包自己做（`TimeoutScope` + `Task.WaitAsync` 把调用方摘出去，SDK 那条后台任务挂 `ContinueWith` 观察掉）。
- **默认值会悄悄让功能不工作。** `SubscriptionOptions.PublishingEnabled` 在 2.0 **默认 false**：监控项能建好、订阅也能建好，但一个通知都不会来。这种"建好了却不工作"的默认值必须显式打开，否则会被误判成"功能没实现"。
- **SDK 自带的测试服务器也有坑，而且比想象的深。** 本期用通用宿主（`HostApplicationBuilder` + `AddOpcUa().AddServer(...).AddNodeManager(...)`）托管官方服务器，四个坑记在 [[协议细节/OPC UA 客户端]] 的"测试服务器"一节：`OperationLimits` 默认 null、只写 `OnRead` 服务器永远回 `BadWaitingForInitialData`、自定义 NodeId 工厂会让服务器起不来、`AddNodeManager` 的回调在宿主启动期间调用（此时连上去是 `BadServerHalted`）。**通用宿主的启动方式**：服务器起好之后用一次真实会话探一次，成功或被策略挡住（`NotSupported` / `AuthenticationFailed`）才算就绪。

**依赖版本提升的处理**：SDK 2.0.1 把 `Microsoft.Extensions.*` 带到 10.0.12 以上，测试项目显式引用旧版本会直接 NU1605 降级错误。做法是**在测试项目自己的 csproj 里 `PackageReference Update` 提到同一版本，不改共享的 `Tests.props`**（改了会让 `build/test-affected.ps1` 的选择范围扩大到接近全量），并在包 README 开头写明这一依赖影响。

**测试替身要能读出服务器侧的数**（P6.2 验收）：会话泄漏、释放过的订阅在重连后复活、"调用方取消之后 SDK 后台照样连上"——这三个缺陷从客户端侧完全看不出来，执行者因此把对应的变异体记成了等价变异体。OPC UA 的做法是给宿主的 `IOpcUaServerFactory` 包一层，把服务器实例记下来读 `SessionCount` / `SubscriptionCount`。新 SDK 的测试替身一开始就要提供这类计数。

**SDK 的"转移 / 恢复"不是免费的**：交给 SDK 恢复的资源（OPC UA 的订阅）要由本包保证"释放的已经从 SDK 的登记里摘掉、还登记着的没有被释放"，否则恢复时会复活或直接让恢复失败（F30、F32）。

**薄适配层的规模对照**：OpcUa 有效行 1758、`Sdk/` 占 64.7%；Mqtt 1484 / 34.2%。OPC UA 的 `Sdk/` 占比高不是因为适配层厚，而是因为值映射（两张表）、NodeId 文本与错误映射表都算进去了——SDK 把分批、继续点、重连、订阅转移都做好了，本包一行都没重写。

## 八、P2 与 P4 摩擦记录中的陷阱

完整记录见计划第 20.2 节（P2 在设计文档第 20.2 节、P4 在第 20.5 节）。

P2（MELSEC）：

- 构建钩子返回 `void`，不能报告错误；可表示性检查放在 `ValidateRange`，编码器保留同一条件的守卫。
- 派生地址的设备属性需要 `new` 隐藏，调用方取具体设备要向下转换。
- `IFrameCodecFactory` 拿不到 `MaxFrameLength`；自定义分帧器需要自己保存上限，并与通道配置保持一致。
- `ChannelComponents` 会静默覆盖同名的传输配置设置；协议的配置方法要守卫。
- 通道族的统计对象构造函数与透传编码器是 internal；测试替身需要通过 `DuplexClientChannel` 或 Testing 的测试底座获得，而不是反射。
- 4C 格式 5 的分帧器要跳过成对的 `10H 10H`，之后才能找到未转义的 DLE ETX；当前实现每次到达都重新扫描缓存的字节，这是待 Channels 提供前进式读取器后改进的已知问题。

P4（S7 与 FINS，编号 F1–F11）：

- 声明式软元件表只能表达"一个数字"的地址；`DB1.DBW12` 有两个数字且宽度字母决定位号必须还是禁止，S7 只能自写解析器（F1）。FINS 的 18 个符号（含 `E0_`–`EC_`）用套件解析器 + 十进制位号进制即可，说明模型的边界在"多段数字"而不是进制或前缀。
- 套件的 `PlcLayout` / `PlcBitPacking` 是 internal，协议拿不到"字节 ↔ 位"的向上取整；加 IVT 会被架构守卫拦下（生产程序集之间的 IVT 固定 2 条），只能各写 3 行（F2）。
- 进程级序号计数器曾经有三份同骨架实现（13–14 行）。`dupscan.py 6` 抓不到它们（可比非空行不足 6 行），"扫描器安静"不等于没有重复。**P4.5 已解决**：Core 的 `Junevy.Communication.Core.Utils.SequenceCounter`（`NextUInt16()` / `NextByte()`，线程安全、第一次返回 1、按宽度回绕）。新协议在**写这个字段的那个类型**上放一个进程级 `static readonly` 实例，让客户端请求与心跳探测共用它；一个实例只按一种宽度用（F3）。
- 通道组件守卫与"接线顺序"（守卫 → 拒绝数据报 → 分帧 → 关联 → 初始化器 → 探测工厂）曾在三个协议之间逐字相同，是 P4 生产重复窗口从 33 升到 54 的全部来源。**P4.5 已解决**：`PlcComponentWiring.Apply(components, owner: nameof(XProfile), frameCodec:, correlation:, keyExtractor:, initializer:, healthProbeFactory:)` 统一守卫与赋值，F4 + F9 都归它。新协议只写两样：交付方式 / 介质的规则（**在调用之前**检查），以及各字段的值。协议总是拥有分帧、关联、键提取器、心跳探测与心跳探测工厂五项（调用方已设置即抛 `ArgumentException`，不静默覆盖）；`Initializer` 只在协议提供初始化器时才算协议拥有，`initializer: null` 时调用方自己的握手钩子原样保留；`ReconnectPolicy` 不碰。**不要为了指标把六个 `if` 改写成数据驱动循环**——文本不再相同而逻辑照旧重复，属于为骗过扫描器改写实现（F4、F9）。
- 钩子是 `protected internal`，`internal` 那一半对协议自己的测试程序集无效：钩子只能经"已连接的客户端"断言。上限是常量时（FINS 999/996）无处可搬，纯算术的期望也要拖着通道与替身跑一条真流水线（F5）。
- `TcpClientChannel` 在构造期校验配置，`Port = 0` 直接抛 `ArgumentOutOfRangeException`；任何"只验证 `Create` 守卫、并不连接"的用例都要先有一个合法端口，且 `Create` 的 null 守卫必须排在创建通道之前才可达（F6）。端口字面量本身用共享测试库的 `LoopbackTcp.Client(port)`（**P4.6 已解决**）：它返回 `127.0.0.1` + 指定端口的配置，可链式 `.WithHeartbeat(...)` / `.Reconnecting(...)`，S7 / FINS / MELSEC 三方共用，不必再各写一遍。
- 大端字段读写（写原样字节、从头部取一个字段且字节不足时返回失败而不是抛）曾由每个协议各写一份，`ByteTransform` 在长度不足时抛异常，不满足解码器的"结构错误走结果"（Q7）。**P4.5 已解决**：Core 的 `Junevy.Communication.Core.Buffers.BigEndianFields`——`WriteUInt8/16/24/32(IBufferWriter<byte>, …)`、`WriteBytes`、`TryTakeUInt8/16/24/32(ref ReadOnlySpan<byte>, out …)`、`TryTakeBytes(…, length, out …)` 与 `UInt8Bytes`…`UInt32Bytes` 四个宽度常量。读取在字节不足时返回 `false`、不移动切片、`value` 取默认值；只有参数错误（`output` 为 null、`UInt24` 越界、长度为负）抛异常。新协议直接用，不要再写第四份（F8）。
- 端到端故障用例的真 TCP 脚手架（`ScriptedTcpServer.Start` + `TaskCompletionSource(RunContinuationsAsynchronously)` + 重连/心跳选项）在两个协议之间同形（F10）。**P4.6 已解决**：`LoopbackTcp.Client(port)` / `Reconnecting(port, …)` / `WithHeartbeat(port, …)`（三个独立的静态工厂，不能链式调用）与 `Arrival.WithinAsync(task, ms)` 都进了共享测试库，三个协议的故障用例共用；协议相关的部分（替身、握手计数、逐字节断言）仍留在各测试项目。
- `CommResult<T>.Data` 声明为 `T?`。**P4.5 已解决**：`CommResult<T>.IsSuccess` 带 `[MemberNotNullWhen(true, nameof(Data))]`，`CommResult` 与 `CommResult<T>` 的 `IsSuccess` 都带 `[MemberNotNullWhen(false, nameof(ErrorMessage))]`。因此 `if (result.IsSuccess)` 分支里直接写 `result.Data`，失败分支里直接写 `result.ErrorMessage`，**不需要** `?? 默认值`，也不需要 null-forgiving 运算符。不变式由 `CommResult<T>.Success` 拒绝 null `data` 保证，所以约定 `T` 不是可空引用类型；"成功但没有值"用 `Fail` 表达（F11）。
- 上述 F3、F4/F9、F8、F7、F10 都是"第四个协议必然再写一遍"的结构性重复，**现已全部解决**：F3、F4/F9、F8 在 **P4.5** 抽成 Core / Plc 的共用件（`SequenceCounter`、`PlcComponentWiring`、`BigEndianFields`）；F7、F10 在 **P4.6** 抽成共享测试库的 `PlcByteMemory`、`LoopbackTcp` 与 `Arrival.WithinAsync`（`Polling.WaitUntilAsync` 同时收掉了 7 份手写轮询）。第四个协议不再写第四份；**只剩 F5（钩子测试门面）按用户决定仍不做**——协议钩子继续经"已连接的客户端 + 替身"测试。

## 九、自有模型协议（不走 Plc 套件）：P5.1 的 SECS-II / HSMS

本节面向**不是地址型**的协议。SECS-II 是第一个：它没有地址、没有软元件、没有类型化读写，因此第一节到第七节（Plc 套件的骨架与钩子）**整体不适用**，只适用"架构先行""不修改通道族""先写测试""文档与回写"这几条。完整笔记见 [[协议细节/SECS-II 与 HSMS]]，作者视角的 Skill 是 [Skills/using-junevy-secs/SKILL.md](file://Skills/using-junevy-secs/SKILL.md)。

### 与地址型协议的差别

| 维度 | 地址型（MELSEC / S7 / FINS） | 自有模型（SECS-II） |
|---|---|---|
| 套件 | `Junevy.Communication.Plc` + 协议包 | **没有套件**：直接引用 Core + Channels + Tcp |
| 公开模型 | `PlcAddress` + 类型化读写 | 协议自己的消息模型（`SecsMessage` / `SecsItem`）与结果类型（`SecsResult`） |
| 状态 | 通道的 `ConnectionState`（+ 协议快照） | 协议自己的状态（`HsmsState` 三态），**不压成 `ConnectionState`** |
| 关联 | S7 / FINS 走 `Sequential` + 回显校验 | 走 `Keyed`，键由协议自带的 `IFrameKeyExtractor` 给出 |
| 目录 | 帧编解码 + 设备表 + 钩子 | `Protocol/`（只碰字节）+ `Hsms/`（会话语义）两层 |

### 必写的三块

1. **消息模型与编解码**（`Protocol/`，无通道依赖）：报文的组装与解析、数据项编解码、SML 文本。防御上限要在**切之前**判定（声明了多长的载荷都不先按声明分配内存），结构错误走结果不抛异常。
2. **会话语义**（`Protocol/` 里的握手 + `Hsms/` 里的设备端）：握手按标准实现成 `IConnectionInitializer`；会话状态用一个内部类型做单一来源，事件按顺序在锁外派发。
3. **派发与结果**：收到的主消息按"会话号 → 正文 → 处理器 → 调用"判定，S9 / 中止类系统消息由**一处**构造；发出的消息走统一的 `SendAsync` 返回结果类型。

### P5.1 的摩擦记录结论（SECS 侧只有两条，都在"握手期间逐帧消费报文"这一个用法上）

- **F1（通道侧，已修）**：`FrameRouter.RouteAsync` 先 `TryComplete` 再 `ClassifyUnclaimed`，两步各自加锁；接收等待者的注册取同一把锁，因此一帧可能落在两次加锁之间——**双方谁也等不到谁**，帧一直躺在握手积压里直到握手结束。**已修**：分支 `fix/channels-handshake-backlog-race`（提交 `5f50ebe`）把两步合并为一次加锁的 `PendingRequestTable.Route(frame, remote, out claimed)`。2026-10-14 已合入 master，SECS 随即去掉了 200 毫秒轮询。
- **F2（文档，已修）**：`IByteChannel.ReceiveAsync` 不给超时时用通道的 `RequestTimeout`（TCP 默认 2000 毫秒），比协议的握手窗口 T7（默认 10000 毫秒）小得多，主机合法地沉默就会被判失败。**已修文档**：同一提交补齐了默认超时的语义。行为不变，但**协议侧的应对与 F1 无关，必须保留**：每次 `ReceiveAsync` 都显式给超时（SECS 给 T7），不要用默认值。
- **由此得到的一条通用结论**：**"在握手窗口内逐帧消费报文"是一个通道族目前没有保证的用法**。F1 修复之后它已有保证；新协议照做时只需记住 F2：每次等待显式给超时。派发路径不受影响（握手已结束，未认领的帧直接进派发队列）。

### 其他容易踩的四处

- **取键规则要自己写死并写进文档**：`Keyed` 关联只提供机制，"哪些消息取应答键"是协议的义务。SECS 的规则是只有应答类消息取应答键——否则对方主消息的 System Bytes 恰等于我在途请求时会被错认成应答（见笔记的"取键规则"一节）。
- **帧事件不等待**：`FrameReceived` 是"逐个隔离异常地调用"而不是 `await`，因此"按到达顺序逐个处理处理器"**不是**通道免费给的语义，需要协议自己串行化；停止时要排空在途的派发，并用 `AsyncLocal` 识别"处理器内部调用 `StopAsync`"以免等自己（P51 偏差 D20）。
- **协议计时器不要塞进通道的通用超时**：T3 是"每个带 W 位消息各自的等待时限"，对应 `RequestOptions.Timeout`；塞进 `RequestTimeout` 会让"事务超时"变成"链路超时"，需要配 `ResetOnRequestTimeout = false` 才不会误断链。
- **别把模式开关做成两份实现**：SECS 的 Passive / Active 只在"通道类型、握手钩子、取得当前连接的方式"上不同，状态、派发、发送、日志、结果类型全部共用（计划 Q26）。写完 Passive 再写 Active 时，先检查差异是不是只有这三样。

### P5.1 验收发现的六处（2026-10-14）

执行者的 251 条用例全绿，审阅时仍找到六处缺陷（另有一处资源释放不完整），修复后 Secs.Tests 为 264 条。它们有共同的来源，写新协议时逐条对照：

- **每条发出的报文先问"它是应答还是新发起"**：应答回送对方的 System Bytes，新发起取自己的计数器。S9 是设备端新发起的主消息，却沿用了被涉及消息的号，主机会把它当成那条主消息的应答。黄金向量里的号不可预测时，**不要把它整个替换成"实际收到的值"**——那等于不比，至少断言"号与被涉及消息不同"与会话号。
- **计划里的规则不能因为"不可达"就静默放弃**：PType ≠ 0 应回 `Reject.req` 原因 2，执行时因为解析器先把它当结构错误拒掉而记为"不可达"，代码直接丢弃，偏差记录里却写着会回 S9F7。真不可达就改结构让它可达，或者停下问。
- **通道的 `DisconnectAsync` 是"用户主动断开"，会永久停止重连**：协议层的"对方结束会话"（`Separate.req`）不等于用户不要连接了。主动端仍处于启动状态时，要么自己按协议间隔再连，要么别用 `DisconnectAsync`。这与 P6.1 的缺陷 R1（停止被当成永久停止）是同一类。
- **停止与释放必须能打断进行中的启动**：启动用一个与停止共用的取消信号；否则主动端等握手时释放，要等满握手超时才返回。
- **选项校验不要比同族的包更严又不记偏差**：主动端的 `Host` 只接受 IP，而 Melsec / S7 / FINS 经同一个 `TcpClientChannel` 都接受主机名。
- **按字节取值的表要按完整字节查**：判断"这个 Stream 有没有处理器"时循环上界误用了 Stream 的上限 127，Function 128 以上的处理器查不到。
