仓库 `AGENTS.md` 的硬性要求（智能体必须逐条遵守，适用于仓库内全部项目）+ 多目标框架技术约束（Modbus 与通道族分别说明，见下文）。

## AGENTS.md 硬性约定（7 条）

1. **架构先行**：开工前设计好架构，考虑扩展性、维护性、耦合性；不为图快随手写逻辑。
2. **CHANGELOG 强制**：修改/新增任何逻辑后必须更新 `CHANGELOG.md`，**注明更新日期**与新增（修改）内容。格式参考 Keep a Changelog，版本遵循 SemVer。
3. **Skills 检索**：设计功能或 API 变更，必须检查仓库 `Skills/using-junevy-modbus/SKILL.md` 是否需要同步更新（它描述了 API 面、重命名陷阱与行为契约，过期会误导其他智能体）。
4. **README 同步**：破坏性更新或涉及 README 内容的更改，必须更新对应包的 README（英文；Modbus 为 `Junevy.Communication.Modbus/README.md`）。根 `readme.md` 只有项目简介与协议索引（2026-10-12 起），新增协议或包、包的定位变化时更新其中的表格。
5. **清理冗余**：功能开发/修改后必须清理无效逻辑代码。
6. **代码风格**：输出代码遵守当前类库风格（XML 注释中英混排现状、`PascalCase`、四空格缩进、region 式分组注释 `// ———— xxx ————`）。
7. **完整验收**：不能以 0 编译错误为目标，必须完整测试符合预期——见 [[测试/测试工程与验收方式]] 的验收清单。"完整"指受改动影响的测试项目全部通过，不是每次跑全量（2026-10-13 起，范围由 `build/test-affected.ps1` 按项目依赖选出）。

## 补充工作约定（AGENTS.md 其他要求）

- 不明确的功能**必须提问**；可扩展的功能必须询问是否扩展；发现更优实现方式必须先检索再询问是否采用。

## 多目标框架技术约束（net472 生存指南）

**Modbus 库**（P7 后为 3.0.0-preview.1，Plc 套件的协议包）多目标 `net472;net8.0`，源码**必须**双目标编译（通道族的约定见下文"通道族（P1，2026-10-10）开发约定"）：

| 禁用（net472 无） | 替代 |
|---|---|
| `Task.WaitAsync()` | 经典的 `Task.WhenAny` 与超时任务竞速，或 `#if NET8_0_OR_GREATER` 分支（见通道族 TCP 连接的实现） |
| `ArgumentNullException.ThrowIfNull` | 经典写法 `if (x == null) throw new ArgumentNullException(nameof(x));` |
| 其他 .NET 6+ API | 同上条件编译，并为 net472 提供降级实现 |

- 确需新 API 时用 `#if NET8_0_OR_GREATER` 并写清 net472 降级行为差异（现有注释模式：net8 取消即时生效 / net472 下一个 I/O 边界生效）。
- **Modbus 库项目不新增外部包依赖**：P7 后 `Junevy.Communication.Modbus.csproj` 只引用本仓库的 Plc、Tcp、Udp、Serial 项目。通道族按设计 Q3 允许微软一方包，见下文。
- 错误消息统一**英文**；改措辞必须同步更新依赖该文案的测试（消息文本钩子是子类覆写的原因之一）。
- 只提供异步公开 API（`ConnectAsync`、`ReadAsync` 等），不做同步版本。Modbus 2.x 的同步 + 异步双轨（`Request`/`RequestAsync`）已在 P7 移除（设计 Q2、P7-D13）。

## 通道族（P1，2026-10-10）开发约定

以下约定来自计划第 0、1 节与设计文档，适用于通道族与 P7 之后的 Modbus。

1. **只提供异步 API**（设计 Q2）。库内每个 `await` 都使用 `ConfigureAwait(false)`。
2. **依赖规则**（设计第 3.1 节；Q3、R1）：
   - 只向下依赖；同层协议包之间互不引用。
   - Core 不依赖 `System.IO.Pipelines` 与 `System.Threading.Channels`。
   - Channels 允许微软一方包（Pipelines、Threading.Channels）；第三方包只允许出现在 SDK 适配包中。
   - 传输包（Tcp、Udp、Serial）只依赖 Channels；Serial 另依赖 `System.IO.Ports` 8.0.0。
   - Channels 对 Tcp、Udp 开放 `internal`，Serial 不开放；第三方传输只能使用公开基类 `StreamClientChannel`（D12）。
   - **生产程序集之间不再新增 `InternalsVisibleTo`**（P2.5，P25-D2）：上一条的两处是登记在案的例外；其他包（Plc、各协议包、新传输）缺什么能力就补公开 API，不靠友元。`Tests/Junevy.Communication.Architecture.Tests` 强制该规则与分层表（例如 Plc 不得引用任何传输包），违反时测试失败。
3. **库项目设置**（D2、D3）：
   - 各库 csproj 显式 `<Import Project="..\build\Junevy.Communication.Common.props" />`。**不新增** `Directory.Build.props`，避免影响 Modbus。
   - `Common.props` 设定 `net472;net8.0`、`Nullable`、`LangVersion=latest`、`GenerateDocumentationFile`、`TreatWarningsAsErrors=true`、`Version=1.0.0-preview.1`；net472 额外编译 `build/Polyfills/*.cs`。
   - **不抑制 CS1591**：公开成员必须有 XML 注释。P7 之后 Modbus 也不抑制（2.x 的抑制已移除）。
   - 新库项目编译无警告（`TreatWarningsAsErrors`）。
4. **测试项目设置**（D4）：
   - 显式 `<Import Project="..\build\Junevy.Communication.Tests.props" />`；双目标 `net8.0;net472`。
   - `TestTfmsInParallel=false`：两个目标的测试进程串行运行，避免同时抢占端口与线程池。
   - 测试项目不 Import `Common.props`，因此不生成 XML 文档，也不把警告当作错误。
   - net472 测试宿主需要 `System.Memory` 的绑定重定向：`build/Junevy.Communication.Tests.app.config` 经 `AppConfig` 复制到各测试程序集的 `.dll.config`（原因见 [[测试/测试工程与验收方式]]）。
5. **配置校验**（D5）：非法配置抛 `ArgumentException` 系列；不改写调用方的配置对象。
6. **net472 禁用清单**（计划第 1 节第 4 条）：`Task.WaitAsync`、`ArgumentNullException.ThrowIfNull`、`Index` 与 `Range`（`^1`、`a..b`）、`init` 访问器与 `record`、`ArrayBufferWriter<T>`。确需新 API 时用 `#if NET8_0_OR_GREATER`，并在注释中写明 net472 的降级行为（`UdpDatagramTransport` 的 `SIO_UDP_CONNRESET` 即一例）。可空性特性（`NotNullWhen`、`MaybeNullWhen`、`DoesNotReturn`）由 `build/Polyfills/NullableAttributes.cs` 提供。
7. **代码风格**（计划第 1 节第 4 条）：文件作用域命名空间（与 `ModbusClient.cs` 一致）；分组注释使用 `// ————— xxx —————`；错误消息与日志用英文，XML 注释用中文；TX/RX 十六进制日志只在 `logger.IsEnabled(LogLevel.Debug)` 时生成，避免提前求值。
8. **套接字测试**（计划第 1 节第 5 条）：放入各测试项目的 `SocketTiming` 集合（同集合串行，与纯内存测试并行）；除专门测超时的用例外，`ConnectTimeout` 统一设为 10000；耗时断言使用区间，下限取期望值的 80%，上限取期望值加 2000 ms；纯内存测试不加集合，否则会损失并行度。
9. **CHANGELOG**（计划第 1 节第 6 条）：通道族的条目写入 `CHANGELOG.md` 顶部的 `## [Unreleased] — 通讯通道族 P1` 节，格式 `- YYYY-MM-DD [包名] 内容`，日期为执行当天。
10. **不动 Modbus**（P1 计划第 1 节第 8 条）：只在 P1 至 P6 期间适用。P7 按自己的计划迁移了 Modbus，之后 Modbus 与其他协议一致，不再有这条例外。
11. **目录与命名空间**（2026-10-18 整理）：项目根目录不放源文件，按职责分到子目录。公开类型常用 `Client/`、`Options/`、`Models/`、`Addressing/`、`Abstractions/`、`Interception/`、`Events/`、`Factory/`；内部实现用 `Lifecycle/`、`Connection/`、`Protocol/`、`Framing/`、`Pipeline/`、`Sdk/` 等。**移动文件不改命名空间**：公开类型留在包的根命名空间（与 Channels、Plc、Tcp 一致），只有本来就有子命名空间的目录（`Sdk`、`DependencyInjection`、`Protocol`、`Framing`、WebApi 的分层命名空间等）才与目录同名。新增文件按同样的方式放。

## WebApi（P3.1，2026-10-12）开发约定

WebApi 是**单程序集，按命名空间分层**（计划 P3-D2、D6、D18）；依赖方向写在 `Tests/Junevy.Communication.Architecture.Tests/WebApiLayeringTests.cs` 的分层表里，违反时测试失败：

| 命名空间 | 允许依赖（WebApi 内部） |
|---|---|
| `Junevy.Communication.WebApi`（根：公共契约、配置、拦截器与事件类型、`IWebApiSerializer`） | 无 |
| `….Serialization` | 根 |
| `….Auth` | 根 |
| `….Http`（全部 internal） | 根、Auth |
| `….Rest` | 根、Serialization、Http |
| `….Soap` | 根、Http（Rest 与 Soap 互不引用） |
| `….Factory` | 根、Rest、Soap |
| `….DependencyInjection` | 根、Factory |

- **NetArchTest.Rules 1.3.2 只出现在 Architecture.Tests**（MIT，仅测试项目，不违反设计 Q3）；它读 IL，方法体里的引用也检查，反射做不到。规则：每个命名空间（正则精确匹配，不含子命名空间）不得依赖表中未列出的 WebApi 命名空间；程序集里出现表外的命名空间本身就是失败；程序集层面 WebApi 只允许引用 Core。新增命名空间（例如 3.2 的 `Server`）先在表里加一行。
- 不要为了绕过分层把类型放进根命名空间；`Http` 不认识 REST / SOAP（协议层只传入"响应 → 结果"的委托）。REST 与 SOAP 共有的行为只在 `Http` 与根命名空间实现一次，两个外观各不超过 200 行。
- 条件编译只在 `Http/HttpHandlerFactory.cs`；net472 禁用清单照旧（另外：net472 的隐式 using 不含 `System.Net.Http`；`HttpResponseMessage.Content` 在 net472 上可能为 null；`XmlSerializer` 在 net472 与 net8.0 上给命名空间选的前缀不同，所以序列化时给显式命名空间表）。
- 不碰进程级状态：不改 `ServicePointManager` 的静态属性，不设置全局 `JsonSerializerOptions`，不注册全局证书回调或代码页提供程序。`XmlSerializer` 只用 `new XmlSerializer(Type)` 与 `new XmlSerializer(Type, string)`。
- 测试：`StubHttpHandler`（`TestSupport/`，所有 WebApi 测试共用，不要再写第二个）驱动绝大多数用例；真实套接字用 `RawHttpServer`（`TcpListener`）并放进 `SocketTiming` 集合；等待用 `TaskCompletionSource` 或带超时的 `SemaphoreSlim`，不复制 `WaitUntilAsync`。README 里的示例代码同时放在 `ReadmeSamples.cs`，由 `ReadmeSampleTests` 运行并检查逐字一致：改一处必须改另一处。
- 文档同步义务：公开 API / 行为契约变化 → `CHANGELOG.md`（`[Unreleased] — WebApi P3.1` 节）、`Junevy.Communication.WebApi/README.md`、`Skills/using-junevy-webapi/SKILL.md`、本库 [[WebApi/WebApi 客户端与钩子]] 与 [[WebApi/重试与可用性行为契约]]；设计修订写入设计文档第 20.4 节。

## SDK 协议适配包（P6，2026-10-12）开发约定

P6 起的包（Mqtt / 未来的 OPC UA / FTP）**只面向 net8.0**，不受"全仓库 net472 双目标"约束，但其余约定照旧。做法细节见 [[Agent协作/新增协议指南]] 第七节，协议细节见 [[协议细节/MQTT 客户端]]。

- **公开 API 里不能出现 SDK 的类型。** 对外的每个概念写本库的薄类型；SDK 类型只允许出现在 `Junevy.Communication.<包>.Sdk` 命名空间，且全部 `internal`。同名时用 `using SdkXxx = Vendor.Xxx;` 别名。
- **依赖只有 Core 与自己的 SDK**，不引用 Channels / Tcp 等传输包；DI 需要的 `Microsoft.Extensions.DependencyInjection.Abstractions` 经 Core 传递，不要在包里再引用一次。
- **"SDK 的错误 → `CommErrorKind`"只允许出现在一个 internal 类型里**（Mqtt 是 `Sdk/MqttErrorMap`），**映射表每一行都要有一条测试**。别处不得再写一份判断。
- **SDK 行为必须由测试钉住**：适配代码依赖的每一条 SDK 行为都要有一条直接验证它的测试（实测行为与计划第 18.2 节的摩擦记录）。这是薄适配层最大的风险。
- **不要重复实现协议里已有的校验**，交给 SDK 的校验器，只把抛出的异常翻译成结果；确需补判断时（如 SDK 未把某属性判为版本专属）写测试说明理由。
- **新加一个 SDK 包要在架构测试里登记四处**：`SdkAdapterArchitectureTests.Adapters`（适配程序集、SDK 程序集名前缀、SDK 命名空间、允许引用的库；三条守卫随之生效，允许列表默认只有 Core，服务端另有 WebApi）、`ArchitectureTests.SdkPrefixes`（程序集引用白名单）、`ArchitectureTests.LayerTable`（`#if NET8_0_OR_GREATER`）、`Architecture.Tests.csproj` 里只在 net8.0 生效的 `ProjectReference`。`Architecture.Tests` 的 SDK 相关文件**只编译 net8.0**（net472 下引用不了这些包）。
- **每条新守卫都要先临时制造一次违规确认它会失败（负控），再撤掉。**
- 测试优先用 SDK 自带的测试服务器（MQTT 用 `MQTTnet.Server` 的进程内 Broker）；替身只包一层，把 SDK 的事件字段摊平成自己的 `record`，用例不接触 SDK 类型。真实套接字类仍需 `[Collection(SocketTimingCollection.Name)]`。
- **凭据与正文任何日志级别都不记录**；SDK 的日志只桥接 Warning 及以上（无法逐条确认 SDK 的日志不含敏感数据），类别 `<包全名>.Sdk`。
- 文档同步义务：`CHANGELOG.md`（`[Unreleased] — P6.1（Mqtt …）` 节，P6.2、P6.3 各自一节）、包内 `README.md`（公开 API 全写 + 验证状态）、`Skills/using-junevy-<协议>/SKILL.md`、本库 [[协议细节/MQTT 客户端]] 与 [[架构设计/通讯库总体架构（协议族）]] 的 P6 行；设计修订写入设计文档第 20 节（本次为 20.8）。

## 代码质量验收（P2 起，P2.5 补充）
