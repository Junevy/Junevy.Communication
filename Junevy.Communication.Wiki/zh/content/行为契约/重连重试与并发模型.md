## 重试语义（RetryCount / RetryInterval）

- `RetryCount` = **首次失败之后**的重试次数；总尝试次数 = `RetryCount + 1`（`GetAttemptCount` 里 `Math.Max(1, ...)` 兜底，负数不会产生 0 次尝试）。
- 每次失败后等 `RetryInterval` 毫秒再试（同步 `Thread.Sleep` / 异步 `Task.Delay`——异步等待可被取消令牌打断）。0 或负值 = 不等待。
- 全部尝试失败 → 返回**最后一次**的结果；任何一次成功 → 立即返回成功。
- 测试基线：`TcpClient_RetryCount_RetriesThenSucceeds`（第一次不应答、第二次成功，断言请求次数 2–3）。

### 重试与重连是耦合的（2026-10-07 修正）

**TCP 的 `Timeout` / `ConnectionClosed` 必须换新连接才能重试**——半包超时后 socket 缓冲区残留半帧，同一连接上重发必然读错。因此骨架按失败类型分派（同步 `ExecuteRequestWithRetry` 与异步 `ExecuteRequestWithRetryAsync` 规则完全一致）：

| 失败类型 | `Reconnect = false` | `Reconnect = true` |
|---|---|---|
| 尝试开始时 `IsConnected == false` | **立即**返回 `Fail(NotConnected, ConnectionClosed)`，不等 `RetryInterval`、不再尝试 | 调 `EnsureConnected(Async)` 重连；失败则等 `RetryInterval` 后下一次尝试 |
| `SendFrame` 返回 false，或收发抛通信异常 | `InvalidateConnection()` 后**立即**返回（`ConnectionClosed`） | `InvalidateConnection()` → 等 `RetryInterval` → 下一次尝试（新连接） |
| 接收失败且 `RequiresNewConnection(result) == true`（TCP 的 Timeout/ConnectionClosed） | `InvalidateConnection()` 后**立即**返回该接收结果，**保留真实 `ErrorKind`**（如 `Timeout`） | `InvalidateConnection()` → 等 `RetryInterval` → 下一次尝试 |
| 接收失败且 `RequiresNewConnection == false`，且非 `ModbusException` | 同一连接上等 `RetryInterval` 重试，次数受 `RetryCount` 限制 | 同左 |
| `ModbusException`（从站异常响应） | 立即返回（终态，绝不重发） | 同左 |

**为什么这样定**：`Reconnect = false`（默认）+ `RetryCount = 3` 曾经会让第一次读超时把连接销毁后，后续 3 次尝试全部在 `EnsureConnected` 处立即失败，最终把真实的 `Timeout` 覆盖成 `Not connected`（`ConnectionClosed`）——错误信息误导现场排查，且白等 3 个 `RetryInterval`。现在 `Reconnect = false` 时超时直接以 `Timeout` 返回，调用方自己决定是否 `Connect()` 重来。

测试基线：`TransportBaseRetryTests`（R1–R9，用 `FakeTransport` 断言调用次数与耗时：R1 `SendFrameCalls==1`、R3 未连接时 `SendFrameCalls==0` 且 <500ms、R2 重连下 `SendFrameCalls==4`/`OpenConnectionCalls==3`、R9 真实 TCP 客户端服务端只收到 12 字节一个请求帧）。

## 重连语义（Reconnect，懒重连）

**没有后台看门狗**。重连只发生在请求路径上，两个触发点：

1. **请求开始前** `EnsureConnected(Async)`：`IsConnected == false` 且 `Reconnect == true` → 无锁核心重建（TCP 新 socket 握手 / RTU 重开串口）；重建失败 → 本轮尝试以 `ConnectionClosed` 失败，走重试。异步路径调用**真异步**的 `OpenConnectionAsync(ct)`（2026-10-07 起；此前是 `Task.Run(OpenConnection)`——占用线程池线程直到连接超时且不响应取消）。
2. **失败之后**（仅 TCP）`RequiresNewConnection(result)`：结果 `ErrorKind ∈ {Timeout, ConnectionClosed, ProtocolViolation}` → 销毁当前连接。动机：TCP 半包超时后 socket 缓冲区残留半帧，必须换新连接才能保证下一次请求读到的是新响应；`ProtocolViolation`（非法 PDU 长度、事务 ID 不匹配、协议 ID 非零、从站号不匹配）之后流中也常有未读字节或迟到的响应，复用同一连接会读到残帧。**2026-10-08 加入 `ProtocolViolation`**。**RTU 恒不按 ErrorKind 重建连接**（基类默认 false，保持现状）。

⚠️ 钩子名 2026-10-07 由 `ShouldReconnectAfterFailure` 改为 `RequiresNewConnection`——它回答的是"这次失败**是否需要**新连接"，而不是"要不要重连"，与上表的重试/重连分派配套。子类覆写签名同步变更。

### ⚠️ Disconnect 后静默重连

`Reconnect = true` 时，显式 `Disconnect()` 之后的下一次请求会**悄悄重建连接**。想让 `Disconnect()` 保持断开（如程序退出、人工维护），必须 `Reconnect = false`（可以另建临时客户端）。

## 并发模型（每连接串行化）

- `SemaphoreSlim requestLock(1,1)`：**Connect / Disconnect / Request / RequestAsync 共用一把锁**——并发 Connect 与 Request 不会让 socket 在收发中途被重建（审查修复 B11；测试 `TcpClient_ConcurrentConnectAndRequest_DoNotInterleave` 8 并发混合 Connect/Request 断言无非白名单异常）。
- 每个客户端实例同一时刻**至多一个在途请求**；重试也在锁内串行。
- 吞吐需求 → 多个客户端实例（工厂多 key），或轮询间隔 > 从站响应时间。
- 工厂/管理器层面线程安全：`ConcurrentDictionary` + GetOrAdd 竞态输家 Dispose + 别名链环检测（见 [[API参考/工厂与依赖注入]]）。

## 事务 ID 与重试（TCP）

`TransactionId` 在**进入重试循环前**于锁内分配一次（`transactionId++`，ushort 回绕）——同一逻辑请求的全部重试**沿用同一 TID**；解析器按精确相等匹配，旧请求的迟到响应永不错配。两次连续请求的线上 TID 依次 0、1（测试 `TcpClient_AssignsSequentialTransactionIds` 固定）。

## 超时语义（ReadTimeout / WriteTimeout）

- **TCP `ReadTimeout` = 收满一个完整响应帧（6 字节 MBAP 头 + PDU）的总时限**，不是每次 `ReadAsync` 的时限；半包在总时限内陆续到达算成功。
- 同步路径靠 `Socket.ReceiveTimeout`，异步路径（`RequestAsync`）由 `ReceiveFrameAsync` 内的 linked CTS `CancelAfter(Config.ReadTimeout)` 强制执行——**2026-10-07 之前异步路径完全不受 `ReadTimeout` 约束**（`Socket.ReceiveTimeout` 只管同步调用），服务端不应答时 `RequestAsync` 永久挂起。
- `WriteTimeout` = 发完一个请求帧的时限；写超时返回 `false`，骨架按"发送失败"归类 `ConnectionClosed` 并销毁连接（与同步路径 `SocketError.TimedOut` 行为一致）。
- 超时返回 `ErrorKind.Timeout`；用户取消返回 `ErrorKind.Cancelled`。两者靠"用户令牌是否已触发"区分。
- net472 上 `NetworkStream.ReadAsync` 不响应取消令牌，实现额外注册回调 **dispose socket** 逼其抛出 `ObjectDisposedException`/`IOException`，由同一个 catch 子句统一归类。
- 测试基线：`TcpAsyncTimeoutTests`（6 个：不应答 / 半个响应头 → `Timeout` 且耗时落在 450–2500ms；延迟 200ms 应答 → 成功；200ms 用户取消 → `Cancelled`；超时后 `IsConnected == false`）。

## 取消语义（CancellationToken）

| 平台 | 行为 |
|---|---|
| net8.0 | 读/写阻塞期间取消**即时生效**（NetworkStream/BaseStream 原生接受 token；TCP 连接期用 linked CTS） |
| net472 | 读/写与**连接**都被"关闭套接字"中断，因此取消同样即时生效（`Task.WaitAsync` 不可用） |

- 取消后返回 `Fail(Cancelled)`（测试 `TcpClient_RequestAsync_CancelledDuringRead_ReturnsCancelledQuickly` 断言 500ms 令牌 5s 内返回）。
- **除 `ConnectAsync` 外**，同步 `Request`、`Connect`、`Disconnect` 无取消支持。
- `ConnectAsync(CancellationToken)`（2026-10-08 新增参数）：令牌在**等待请求锁**与**建立连接**两处生效；**用户取消抛出 `OperationCanceledException`**（`Task<bool>` 无法表达"已取消"），连接失败或超时仍返回 `false`。
- TCP/RTU 的读超时与用户取消都用同一套判别：linked CTS（`CancelAfter(ReadTimeout)`）触发且用户令牌未触发 → `Timeout`；用户令牌触发 → `Cancelled`。TCP 侧 `SendFrameAsync` 用户取消时重新抛出 `OperationCanceledException`。
- 重试间隔等待也接受令牌——取消能打断"重试风暴"立即退出。

## TCP 连接是真异步（2026-10-08）

| 平台 | `OpenConnectionAsync` 实现 | 调用 `ConnectAsync()` 的线程 |
|---|---|---|
| net8.0 | `Socket.ConnectAsync(host, port, CancellationToken)` | 立即返回 |
| net472 | `Task.Factory.FromAsync(BeginConnect/EndConnect)` + `Task.WhenAny` 与超时任务竞速 | 立即返回 |

- 旧实现两处缺陷：net472 直接调用同步 `OpenConnection()`，**调用线程被阻塞到 `ConnectTimeout`**；net8 的 `BeginConnect` + `FromAsync` + `WaitAsync` 在超时后**底层连接仍在后台尝试**，`socket` 被销毁时 `EndConnect` 抛出的异常无人观察。
- 新实现超时时会销毁套接字中止底层连接，并用 `ContinueWith(OnlyOnFaulted)` 观察其最终异常（避免"未观察的任务异常"）。
- 同步 `OpenConnection` 现在在 `finally` 中 `Close()` 一次性的 `AsyncWaitHandle`（此前两条路径都泄漏该内核句柄）。
- 验收证据（net472 探针）：不可路由地址 + `ConnectTimeout=500` 时 `ConnectAsync()` 调用在 **0–9 ms** 内返回且任务未完成，总耗时 ~530 ms。

## RTU Read-until-frame 与噪声容忍

RTU 串口流没有消息边界，接收循环"读一点 → 试着解析 → 不完整/不匹配就等 `FrameReadInterval` 再读"。解析器逐字节扫描跳过噪声（从站 ID 不符的残留字节），CRC 是最终裁决。⚠️ 与 TCP 不同，RTU 的 `ReadTimeout` **只约束单次 Read 阻塞**，"慢从站 + 多次半帧"的总体等待可能超过 `ReadTimeout`——现场调参时注意（响应慢的从站调大 ReadTimeout，脏线路靠 CRC + 重试兜底）。

## Dispose 契约（2026-10-08）

| 时机 | 行为 |
|---|---|
| Dispose 幂等 | 并发调用只有第一个执行释放（`Interlocked.Exchange(ref disposeState, 1)`） |
| Dispose 返回时 | 套接字/串口已关闭；在途请求已退出；不会再有请求使用连接（内部先 `requestLock.Wait()` 等在途请求） |
| Dispose **之前**已进入的请求（在途或排队） | 返回 `Fail(" [Request(Async)] Client disposed.", ConnectionClosed)`，**不抛异常** |
| Dispose **之后**才调用 `Request`/`RequestAsync`/`Connect`/`ConnectAsync` | 抛 `ObjectDisposedException`（使用方编程错误） |
| Dispose 之后调用 `Disconnect()` | 空操作，不抛 |
| 在途 `RequestAsync` 遇 Dispose | 返回 `ConnectionClosed`；**只有调用方自己的令牌**被取消时才返回 `Cancelled` |

- 实现要点：新增 `disposeCts`（`RequestAsync` 用 `CreateLinkedTokenSource(用户令牌, disposeCts.Token)`）与 `disposeState`；`disposed` 改为 `volatile`；`Request`/`Connect`/`Disconnect` 在拿到请求锁之后**再次**检查 `disposed`（Dispose 可能发生在等锁期间）。
- **不再释放内部 `SemaphoreSlim`**：`SemaphoreSlim.Dispose()` 不会唤醒已挂起的 `WaitAsync` 等待者，释放后排队请求会抛 `ObjectDisposedException` 逃逸出结果式 API；且本类未使用 `AvailableWaitHandle`，没有需要释放的非托管资源。
- 旧实现的三个缺陷：在途请求的 `finally { requestLock.Release(); }` 抛 `ObjectDisposedException`；排队请求被永久挂起（测试进程 15 分钟不退出）；TCP 同步路径的 `socket!` 在 `DisposeConnection` 置 null 后抛 `NullReferenceException`（不在 `IsCommunicationException` 白名单内，同样逃逸）。
- 测试基线：`DisposeConcurrencyTests` D1–D10，其中 D1/D2/D3 各循环 20 次。

## 现场调参建议（readme 摘录 + 源码推断）

- 轮询间隔 > 从站响应时间；显式设置三个超时（别依赖默认 2000ms）。
- 长运行服务开 `Reconnect = true` + 合理 `RetryCount/RetryInterval`（如 3 / 200ms）。
- 失败请求带设备上下文记日志（key、SlaveId、功能码、ErrorKind），便于定位接线/网络故障。
