## 总契约

**结果式，不抛通信异常。** `Request`/`RequestAsync` 与全部扩展方法以 `ModbusResult<T>` 表达成败：

- 失败必有 `ErrorMessage`（英文）+ `ErrorKind`（机器可读分类）。
- 成功 `ErrorKind == None`，`Data` 有效。
- 重连/重试/告警决策**只看 `ErrorKind`**，禁止匹配 `ErrorMessage` 字符串（`ErrorKind` 的引入动机，2026-10-05）。

## ModbusErrorKind 全语义表

「库内重试？」与「TCP 需重建连接？」两列都以 `Reconnect = true` 为前提——`Reconnect = false` 时**需要新连接的失败立即返回、不重试**（详见 [[行为契约/重连重试与并发模型]]）：

| Kind | 语义 | 谁产生 | 库内重试？（Reconnect=true） | TCP 需重建连接？ |
|---|---|---|---|---|
| `None` | 成功 | — | — | — |
| `Unspecified` | 未分类（兼容默认） | 裸 `Fail(msg)` 调用 | 是（按普通失败） | 否 |
| `InvalidRequest` | 本地校验失败，未上线 | `CheckRequest` / 扩展方法 | 否（校验发生在重试循环**之前**，直接返回） | 否 |
| `ConnectionClosed` | 连接断开 / 发送失败 / 未能重建 | EnsureConnected、SendFrame、远端关流 | 是 | 是 |
| `Timeout` | 连接/读/写超时 | TCP 读/写超时（同步 socket 超时或异步 `CancelAfter`）、串口 ReadTimeout | 是 | 是 |
| `ProtocolViolation` | 帧格式 / CRC / 长度违规、底层成功但数据过短 | 两解析器、TCP PDU 长度域、扩展方法层短数据检查、RTU 缓冲溢出 | 是（同一连接上） | 否 |
| `ModbusException` | **从站异常响应（终态）** | 两解析器（FC\|0x80） | **否，立即返回** | 否 |
| `Cancelled` | 取消令牌触发 | RequestAsync | 否 | 否 |

## 通信异常的归类与逐层透传

- 骨架捕获白名单通信异常后不再裸 `Fail`（会把 Kind 冲成 `Unspecified`），改用 `ClassifyCommunicationException(ex)`：`TimeoutException` → `Timeout`，其余白名单异常 → `ConnectionClosed`（2026-10-07）。
- **高层扩展方法透传底层 `ErrorKind`**：`ReadCoils`/`ReadDiscreteInputs`/`ReadHoldingRegisters`/`ReadInputRegisters`/`WriteSingle*`/`WriteMultiple*`/`ReadExceptionStatus`/`Diagnostics`/`GetCommEvent*`/`ReportServerId`/`MaskWriteRegister`/`ReadWriteMultipleRegisters` 共 32 个入口（16 同步 + 16 异步）全部 `Fail(result.ErrorMessage, result.ErrorKind)`。此前一律 `Fail(result.ErrorMessage)` 重置为 `Unspecified`——实测底层 `ConnectionClosed`、高层返回 `Unspecified`。
- **底层成功但数据长度不足**（如请求 10 个寄存器只回 1 字节）时，这些方法返回 `Fail("Response data is shorter than the requested quantity.", ProtocolViolation)`，**不再抛 `ArgumentException`**——违反"结果式 API 不抛异常"契约。配套新增内部 `ModbusHelper.TryParseCoils/TryParseRegisters`（不抛），公开的 `ParseCoils/ParseRegisters` 保持抛异常行为不变。
- RTU 接收缓冲在解析出合法帧前被填满 → `ProtocolViolation`（原为 `Unspecified`）。

## Modbus 异常响应的终态保证（三层一致）

从站返回异常响应（功能码 | 0x80，如请求 0x03 回 0x83 + 异常码 0x02）时：

1. **解析器层**：TCP `funcCode == request.FunctionCode | 0x80` → `Fail("Modbus exception response. Function=0x83, Code=0x02.", ModbusException)`（修复 B1：旧版在裸 `Request` 层误报成功）；RTU 还要求 CRC 通过才认，否则当噪声继续扫。
2. **传输骨架层**：`ErrorKind == ModbusException` → 立即返回，**绝不重发**（注释原文 "terminal answers — no resend"；测试 `TcpClient_ExceptionResponse_IsTerminal_NoRetry` 用请求计数固定）。
3. **扩展方法层**：`NormalizeRawResult` 再查 `pdu[1] & 0x80` 兜底（防御直连实现绕过解析器），消息含 `Code=0xXX`。

调用方拿到 `ModbusException` 时**不要自己重试**——那是设备的权威答复（如 IllegalDataAddress = 地址不存在），重试只会骚扰设备。

## 异常逃逸边界（什么情况会真的 throw）

| 情形 | 抛什么 | 层 |
|---|---|---|
| 扩展方法参数校验失败（数量 0 / 超上限 / 空数组） | `ArgumentException` | ModbusExtensions |
| 传 null config / 空 key / RTU 空 PortName | `ArgumentNullException` / `ArgumentException` | 工厂 |
| 非法请求进 `FrameBuilder.GetRequestFrameLength` | `ArgumentException` | Framing |
| `BuildRequestFrame` 构建失败 | `InvalidOperationException` | Framing/ModbusHelper |
| **直接调用 `ModbusHelper.ParseCoils/ParseRegisters` 且数据过短** | `ArgumentException` | ModbusHelper（公开 API，刻意保留抛异常；结果式路径走 `TryParse*`） |
| 客户端/工厂 Dispose 后再调用 | `ObjectDisposedException` | 全部 |
| 通信异常白名单**之外**的内层异常 | 原样上抛（视为缺陷，不吞） | 骨架 |

其余一切通信故障（含协议违规、CRC 错、设备异常）都收敛为 `Fail` 结果——审查修复 B3 保证同步/异步行为一致、非法 MBAP 长度/RTU 零长帧不再逃逸。

## IsCommunicationException 白名单（骨架吞掉的异常类型）

`SocketException`、`TimeoutException`、`IOException`、`ObjectDisposedException`、`UnauthorizedAccessException`、`InvalidOperationException`、`EndOfStreamException`。

这是 TCP 原表与 RTU 原表的**并集**（源码 XML 注释明文取舍理由）：RTU 实际不会遇到 Socket 系列但并集无影响；`InvalidOperationException` 保留是覆盖"串口未打开"场景。捕获后 → 日志 + `InvalidateConnection()` + 返回 `Fail`。

## 面向调用方的处理建议

```csharp
var result = await client.ReadHoldingRegistersAsync(1, 0, 10, ct);
if (result.IsSuccess) { /* use result.Data */ }
else switch (result.ErrorKind)
{
    case ModbusErrorKind.ModbusException: /* 设备答复异常：查地址/功能码，别重试 */ break;
    case ModbusErrorKind.Timeout or ModbusErrorKind.ConnectionClosed:
        /* 网络/接线问题：Reconnect=true 时库已自动重试重连；Reconnect=false（默认）时立即返回，需自己重连 */ break;
    case ModbusErrorKind.ProtocolViolation: /* 固件/干扰/波特率，或响应数据过短：抓原始帧排查 */ break;
    case ModbusErrorKind.Cancelled: /* 调用方主动取消 */ break;
    case ModbusErrorKind.InvalidRequest: /* 编程错误：修参数 */ break;
    default: /* Unspecified：读 ErrorMessage */ break;
}
```

`Unspecified` 现在只可能来自库内的遗留裸 `Fail` 调用——通信失败、协议违规、取消、参数错误都有明确 Kind，落到 `default` 基本意味着"新加的错误路径忘了带 Kind"，值得反馈。

现场排查时打开 Debug 日志可看到 `[TX]`/`[RX]` hex 与毫秒差（LogExtensions），失败帧也会随 `Data` 返回。
