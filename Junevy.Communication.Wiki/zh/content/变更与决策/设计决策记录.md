## 结构决策

### 模板方法合并传输骨架（ModbusTransportBase）

- **背景**：旧 `ModbusTCP`/`ModbusRTU` 各持一份近似重试循环（`ExecuteRequestWithRetry(Async)` ×2、`EnsureConnected(Async)` ×2、`WaitBeforeRetry(Async)` ×2 等四份），合计 1233 行，行为漂移（B3 同步异步不一致就是这么来的）。
- **决策**：骨架收敛到基类——同步 + 异步各**唯一一份**；子类只实现协议钩子。两文件 1233 行 → 752 行。
- **代价与边界**：公开 API 在基类实现，消息文本/校验结果等**逐字差异**用钩子保留（避免文案变化悄悄破坏依赖文案的测试）；`IsCommunicationException` 取 TCP/RTU 两表并集。

### 错误契约统一（ModbusErrorKind）

- **背景**：重连判断曾依赖错误消息字符串匹配——文案一改行为就变。
- **决策**：失败结果携带机器可读 `ErrorKind`；`RequiresNewConnection`（2026-10-07 由 `ShouldReconnectAfterFailure` 改名）只看 Kind；`ModbusExceptionCode` 从字符串解析拆成枚举 + `Describe()` 扩展。
- **推论**：新增错误类别必须先加枚举值，禁止"换个措辞表达新错误"。
- **延伸（2026-10-07）**：`ErrorKind` 现在要**逐层透传**到调用方——高层扩展方法此前用 `Fail(result.ErrorMessage)` 重建结果，把 Kind 冲成 `Unspecified`，等于让新契约在最外层失效。通信异常另加 `ClassifyCommunicationException` 映射（`TimeoutException`→`Timeout`，其余→`ConnectionClosed`），不再裸 `Fail`。

### 参数校验双层化

- **决策**：扩展方法层抛标准异常（编程错误，调用点就能发现）；原始 `Request` 层返回 `Fail(InvalidRequest)`（结果式契约对齐，B3）。`ModbusHelper.CheckRequest` 是原始层权威；`ValidateBitQuantity` 等是扩展层权威。两层阈值**有意不完全相同**（如 0x08：原始层 3–252 字节、扩展层 data 1–250）——B9 修复对齐了 Diagnostics 的矛盾，但保留分层。

### 库不篡改调用者对象（B7）与 config 回填的例外

- `ModbusRequest`：库不修改协议语义字段（协议来自显式参数、DTO 无副作用）；唯一回写 TCP TID（D2 必需，文档明示）。
- `config` 对象：`GetOrAdd/TryAdd` **会**回填默认值（改写传入实例）——这是"补全用户省略项"的既定行为，与"不改请求"的承诺区分对待。若未来要改此行为，属于破坏性契约变更。

### 别名机制（RS-485 多从站）

- **背景**：一条 RS-485 总线一个串口、多个从站；按"每逻辑从站一连接"建模会重复打开同一串口。
- **决策**：物理连接注册一次，逻辑名以**别名**指向它（`Entry` 直连/别名二态、链式解析 + 环检测）；`RemoveAlias` 拒绝主条目。
- **修正（2026-10-07）**：**`TryRemove` 改为级联**——移除直接实例时连带删除所有指向它的别名（含间接链）并释放实例，理由见下。旧设计"有别名时保活实例"是错的：别名一旦解析失败（`Get(alias)` 返回 null），实例就成了既不释放也不可达的孤儿，`Dispose()` 遍历直连条目同样找不到它，串口/套接字永久泄漏。因此现在的规则是**别名与主键同生共死**——想保留实例就别删主键，或把同一实例注册在另一个直接键下（`ReferenceEquals` 守卫保证那时不重复释放）。
- `RegisterAlias` 现在对悬空目标（`existingKey` 未注册）、`aliasKey == existingKey`、`aliasKey` 已存在都返回 `false`——别名链的完整性靠注册时校验，不靠事后兜底。
- `ModbusConnectionManager.GetOrAdd` 不用 `ConcurrentDictionary.GetOrAdd`——其 valueFactory 竞态下可能执行多次且输家泄漏；改为 TryGetValue/TryAdd 自旋 + 输家 Dispose（B4）。

### 无 DI 容器支持（ModbusFactoryBuilder）

- **背景**：Prism/DryIoc/Unity 宿主没有 `IServiceCollection`，但有同样的日志/解析器注入需求。
- **决策**：流式 Builder，未设置项与 `AddModbusFactory` 默认一致；`WithConnectionManager` 允许与宿主容器共享注册表；`Build()` 每次独立实例。库本体**不引用** Microsoft DI 实包（只有 Abstractions）。

### 懒重连而非看门狗

- **决策**：不建后台保活线程；重连只在请求路径两个点发生（请求前 EnsureConnected、失败后按 `RequiresNewConnection` 重建——TCP）。
- **理由**：工业轮询场景下请求天然周期性，看门狗线程引入生命周期/竞态复杂度收益甚微。
- **已知副作用**（文档必须保留的警告）：`Disconnect()` 后请求会静默重连。

### 超时必须覆盖异步路径（2026-10-07）

- **背景**：`Socket.ReceiveTimeout`/`SendTimeout` **只作用于同步调用**。TCP 的 `SendFrameAsync`/`ReceiveFrameAsync` 走 `NetworkStream.ReadAsync/WriteAsync`，完全不受这两个属性约束——`ReadTimeout` 在异步路径上形同虚设，服务端不应答时 `RequestAsync` **永久挂起**（实测 5000ms 后仍未返回）。
- **决策**：异步路径用 `CreateLinkedTokenSource(ct)` + `CancelAfter(ReadTimeout/WriteTimeout)` 自行实施时限；`ReadTimeout` 定义为**收满整个响应帧的总时限**（不是每次 ReadAsync 的时限），这样"半包陆续到达"只要在总时限内完成就算成功。net472 的 `NetworkStream.ReadAsync` 不响应令牌，额外注册回调 dispose socket 逼出异常，由统一 catch 子句归类。
- **为什么不用"每次 ReadAsync 各自的时限"**：那会让慢速分片的从站被误判超时，且与同步路径（`Socket.ReceiveTimeout` 本来就是整次读的超时）语义不一致。
- **配套**：`EnsureConnectedAsync` 改调真异步的 `OpenConnectionAsync(ct)`（`Task.Run(OpenConnection)` 会占住线程池线程直到连接超时且吞掉取消令牌）。

### Read-until-frame + CRC 裁决（RTU）

- RTU 串口流无消息边界，T3.5 静默计时在托管代码里不可靠；改为"累计读 + 逐字节扫描 + CRC 唯一裁决 + `FrameReadInterval` 节流"，容忍噪声与粘包，异常帧也要求 CRC 通过才认。
- 面积代价：接收缓冲 257 字节上界（256 完整帧 + 1 防溢出误判，B8）。

## 通讯通道族（P1，2026-10-10）

记录通道族的"为什么这样做"。来源是设计文档第 20、21 节与实施计划第 0 节的决策表；与代码不一致时以代码为准。以下决策不改变 Modbus，Modbus 的既有决策仍然有效。

### 协议族架构：第二轮审阅放弃统一顶层接口

| 项 | 内容 |
|---|---|
| 背景 | 第一轮设计让所有协议实现统一的客户端接口与 `ConnectionState`，并用统一工厂 `ICommunicationFactory` 创建（取用时 `GetRequired<T>` 强转） |
| 决策 | 按**协议族**组织。族内共享接口与骨架（字节通道族、地址型协议族）；族间只共享无语义工具（Core）。`IConnectable` 只用于"拥有一条字节链路"的对象；不提供跨族统一工厂，各族建自己的工厂（字节通道族为 `ChannelFactory`，地址型族计划为 `PlcClientFactory`），两者都以 `NamedRegistry<T>` 为基础 |
| 被否备选 | 统一的客户端接口加统一工厂 |
| 理由 | SECS 要区分 Not Selected 与 Selected，GEM 有通讯状态与控制状态；OPC UA 有会话、订阅与逐项状态码；WebAPI 没有连接。统一接口会压扁这些语义；统一工厂造成跨族耦合（设计第 1 节；第 20 节第 1、4、5 项） |
| 代价 | 宿主若要"一份配置声明所有设备"，需要在宿主层映射到各族工厂（设计第 16 节） |

### 后台主动重连与 Modbus 懒重连并存

| 项 | 内容 |
|---|---|
| 决策 | 通道族采用后台主动重连（`ConnectionSupervisor`）；Modbus 保持懒重连，本期不改（设计 Q4） |
| 理由 | 设备主动上报时可能长时间没有请求，懒重连无从触发；接收循环常驻，能第一时间发现断线；同时消除"`Disconnect()` 之后下一次请求悄悄重连"的问题（设计第 11.2 节） |
| 代价 | 同一个库内两套重连语义并存。通道的 `Reconnect.Enabled` 默认 `false`，与 Modbus 的 `Reconnect=false` 一致。两者的差异见 [[行为契约/通道重连心跳与超时]] |

### Q2：新模块只提供异步 API

| 项 | 内容 |
|---|---|
| 决策 | Core、Channels、Tcp、Udp、Serial 只有异步公开 API。"同步 + 异步双轨"的约定只适用于 Modbus（设计 21.1 Q2） |
| 理由 | 设计 21.1 Q2：OPC UA、MQTT 等 SDK 本身只有异步接口；新模块依赖常驻的后台循环（接收、派发、心跳、重连），同步版只能阻塞等待异步实现，没有实际价值。实现上，通道的超时与取消也都建立在异步 I/O 之上（`TimeoutScope`、填充循环的取消、net472 下通过关闭套接字中止） |

### Q3：依赖规则放宽为允许微软一方包

| 项 | 内容 |
|---|---|
| 决策 | 允许微软一方的 BCL 扩展包（`System.IO.Pipelines`、`System.Threading.Channels`、`System.Text.Json`）。第三方包只允许出现在 SDK 适配包中（设计 21.1 Q3） |
| 理由 | 字节通道的实现依赖 Pipelines 与 Channels，这两个包由微软维护 |
| 与 Modbus 的关系 | 2026-10-05 计划中的"库项目不新增外部包依赖"是 Modbus 库的约束，不适用于通道族 |

### R1：Core 与 Channels 拆分

| 项 | 内容 |
|---|---|
| 决策 | Core（无语义工具）与 Channels（字节通道族）为两个包。Core 不依赖 Pipelines 与 Channels |
| 理由 | 只依赖 Core 的协议族（WebApi、OPC UA 等）不会被带上 Pipelines 与通道机制（设计 21.1 R1、第 20 节第 8 项） |
| 验证 | `Junevy.Communication.Core` 的 nuspec 依赖为 `Microsoft.Bcl.AsyncInterfaces`、`Microsoft.Extensions.*.Abstractions`、`System.Memory`，不含 Pipelines 与 Channels。补丁任务 C 之后 net8.0 依赖组只剩两个 Abstractions（设计 20.1 第 41 项） |

### R2：P2 先做 Plc 套件与 MELSEC，再做 WebApi

| 项 | 内容 |
|---|---|
| 决策 | P2 为 Plc 套件与 MELSEC MC，用真实协议验证扩展性；P3 为 WebApi（设计 21.1 R2） |

### D1：新包版本为 1.0.0-preview.1，不执行 nuget push

| 项 | 内容 |
|---|---|
| 决策 | 新包统一为 `1.0.0-preview.1`（`build/Junevy.Communication.Common.props`）。P2 验证之后才发布 `1.0.0` |
| 理由 | P2 验证中发现的通道层缺口可能需要调整公开 API，在此之前不承诺稳定版本（计划 D1） |

### D5：配置校验，不回填

| 项 | 内容 |
|---|---|
| 决策 | 新代码校验配置：非法时抛 `ArgumentException` 或其子类（如 `ArgumentOutOfRangeException`），**不改写调用者的配置对象** |
| 被否的做法 | Modbus 式的回填（`GetOrAdd`、`TryAdd` 改写 config 的零值字段，见上文 B7 的例外） |
| 理由 | 回填会让调用方持有的对象与实际运行的配置不一致，是 Modbus 已知的陷阱（计划 D5） |
| 现状 | `Config` 返回调用方传入的对象本身，运行行为只使用构造时的快照（计划第 20 节 Task 10） |

### D7：字节流采用填充循环与解析循环

| 项 | 内容 |
|---|---|
| 决策 | `StreamChannel` 不使用 `PipeReader.Create(stream)`。填充循环把流读入内部 `Pipe`，解析循环从 `Pipe` 分帧 |
| 理由 | net472 的 `NetworkStream` 与 `SerialPort.BaseStream` 不响应取消令牌，`CancelPendingRead()` 打断不了挂起的流读取，静默分帧与半帧计时会失效；内部 `Pipe` 的读端在两个目标上都可靠响应（计划 D7，设计 6.2） |
| 代价 | 每条字节流连接多一个循环与一层内部缓冲 |

### 实施中改变了原设计的修正

| 修正 | 原设计 | 实现 | 依据 |
|---|---|---|---|
| 心跳与 `ResetOnRequestTimeout` | 探测走普通请求路径 | 探测期间的请求超时不重建连接，由 `MaxFailures` 计数。否则 TCP 默认设置下第一次探测超时即断开，`MaxFailures` 失效 | 计划第 20 节 Task 8；设计 5.4 |
| 迟到判定顺序 | 未明确 | 在途请求 → 迟到判定 → 接收等待者 → 积压或派发。`Keyed` 模式的 `RequestAsync` 忽略 `Matcher`，`ReceiveAsync` 仍使用 `Matcher` | 计划第 20 节 Task 5；设计 5.3 |
| 停止时排空 | 未说明 `Dispose` 是否排空 | `DisconnectAsync` 在 `DisconnectTimeout` 内排空；`Dispose` 立即释放、不排空。同步 `Dispose` 的等待上限为 `DisconnectTimeout + 1000` ms（服务端为 `StopTimeout + 1000` ms） | 计划第 20 节 Task 12；D16 |
| `IsConnected` 的位置 | `IByteChannel` 声明 `IsConnected` | 只在 `IConnectable` 上声明。两处同时声明时，经 `IClientChannel` 访问会报 CS0229；`ITcpSession` 自行声明 | 计划第 20 节 Task 3；设计 5.1 |
| 握手期间到达的帧 | 未说明 | 进入积压，上限 64 帧（D8）。字节流溢出按协议违规处理 | 计划 D8 |
| 服务端心跳探测 | 可以共享 `ChannelComponents.HealthProbe` | 构造时拒绝；改用 `ChannelComponents.HealthProbeFactory` 按会话创建（客户端同名工厂以通道自身为参数）。`TcpChannelComponents.SessionHealthProbeFactory` 已删除（preview 期内调整） | 计划第 20 节 Task 9 与补丁任务 A；设计第 20.1 节第 19、39、40 项 |
| 数据报的握手积压溢出 | 设计第 11.1 节写为按 ProtocolViolation 断开 | 丢弃该数据报并计 `ProtocolErrors`，不断开。数据报没有分帧状态可以损坏 | 代码（`DatagramChannel.HandleDatagramAsync`）；以代码为准 |

## SDK 协议适配（P6，2026-10-12，用户确认）

计划：`docs/superpowers/plans/2026-10-12-p61-mqtt.md`（含三期共用的 P6-C1–C14）、`2026-10-12-p62-opcua.md`、`2026-10-12-p63-ftp.md`。设计文档第 14.2、14.3 节与 21.1 节 Q9–Q12。**截至本条写入时三期都还没有执行**，仓库中没有对应的项目。

### 用成熟的第三方库，只写适配层

| 项 | 内容 |
|---|---|
| 决策 | MQTT、OPC UA、FTP 都使用现代、支持异步、经过大量验证的 NuGet 包，本库只写适配层，不从零实现协议：MQTTnet 5、OPC Foundation .NET Standard 2.0.x、FluentFTP。只做客户端 |
| 理由 | OPC UA 规模大且安全部分自己写风险高；FTP 的难点在各家服务器目录格式等兼容细节；这三个库都会自己管理连接与重连，硬套通道族的 Supervisor 会冲突（设计第 20 节第 2 项）。对照：MC、S7、FINS、SECS 自己写，是因为它们是小型二进制帧协议，正好落在 Channels 上，且没有许可证合适、符合结果契约的现成库 |
| 版本 | OPC UA 由用户选定 2.0.x 新版本线（2.0.0 于 2026-10-07 发布），因此 P6.2 的 Task 0 先做 SDK 调研 |

### 只面向 net8.0

| 项 | 内容 |
|---|---|
| 决策 | 三个适配包与它们的测试只面向 net8.0，不做 net472；其余包仍是 `net472;net8.0` |
| 理由 | 用户决定。三个 SDK 的新版本也已不再支持 net472（MQTTnet 5 只有 net8.0 / net10.0；OPC UA 2.0 的 .NET Framework 最低为 4.8）。已知使用方 AutomationSystem 全部是 net8.0 |
| 影响 | 架构测试对这三个包的引用只在 net8.0 下编译；net472 禁用清单不适用于这三个包 |

### SDK 类型不外露

| 项 | 内容 |
|---|---|
| 决策 | 公开 API 只用本库与 BCL 的类型（例如 NodeId 用标准文本、值用 .NET 基本类型、状态码用自己的结构）；包内凡是使用 SDK 的代码都集中在 `Sdk` 命名空间并且是 internal。由架构测试强制 |
| 理由 | OPC UA 2.0 把 API 里的 `object` 换成了 `Variant`；暴露 SDK 类型会让每次 SDK 升级都连带破坏使用方。这改变了设计 14.2 原来"保留原生模型"的写法：保留的是原生**语义** |
| 代价 | OPC UA 的结构体、多维数组等复杂类型本期不支持 |

### 范围与默认值

| 项 | 内容 |
|---|---|
| MQTT | 3.1.1 与 5.0、TLS、MQTT 5 属性、遗嘱消息（文本正文；只在异常断开时由 Broker 发布） |

## P7：Modbus 迁移到 Plc 套件（2026-10-19，用户确认）

计划：`docs/superpowers/plans/2026-10-19-p7-modbus-migration.md`（P7-D1 至 P7-D18）。设计修订：设计文档第 20.12 节。

### 原地替换，不保留 2.x（P7-D1、P7-D16）

- 包名不变，版本 `3.0.0-preview.1`。2.x 的代码与测试从 master 删除（`git rm`），保留在标签 `modbus-v2.0.0`。
- 不加 `[Obsolete]` 转发层（Q29 的既定规则）。迁移说明写在 `Junevy.Communication.Modbus/README.md` 的 "Migrating from 2.x" 一节与 Skill `using-junevy-modbus`。
- **原因**：用户决定原地替换，不保留兼容层。

### 套件只补两项通用能力（P7-D2）

- S1 `IsReadOnly(TAddress)`（虚方法，默认 `false`）、S2 `SendProtocolRequestAsync<T>`（protected）。其余接口不变。
- **原因**：只读地址（`IR`、`DI`）与协议专有请求（0x16、0x17）在其他协议中也会出现，两者都需要操作锁与重试。

### 站号写在地址里（P7-D4）

- 写法 `s=n;HR100`；零基 `HR100` 与一基 `40101` 并存；由自写的 `ModbusAddressParser` 解析。
- **原因**：用户决定站号放在地址前缀里。声明式地址表无法表达站号前缀与一基写法（F-A1）。

### 寄存器的位写入默认拒绝（P7-D5）

- `UseMaskWriteForBits` 打开后用 0x16 原子写入；`AllowReadModifyWriteBits` 打开后才做读-改-写；两者都关闭时返回 `NotSupported`。
- **原因**：读-改-写不是原子的，默认拒绝避免静默的并发错误（与设计 12.6 一致）。

### RTU 定长分帧，MBAP 按事务号关联（P7-D8、P7-D9）

- RTU 放弃 `FrameReadInterval`（IdleGap），按应答的功能码与字节数确定帧长，收全后以 CRC 裁决。
- MBAP 使用 `CorrelationMode.Keyed`，事务号来自进程级计数器；超时后的迟到应答因事务号不符被丢弃。
- **原因**：帧长可由功能码推出，不依赖时序；事务号能消除迟到应答的错配。

### 应答校验与终态异常（P7-D10、P7-D12）

- 构造请求时记下这一包的期望（帧格式、站号、功能码、地址、数量或回显）。异常应答为 `RemoteError` 终态，不重试。
- 心跳探测读 `HR0`；正常应答与异常应答都算健康。

### 连接与重试语义统一为套件的规则（P7-D13，行为变化）

- 懒重连改为通道的后台重连（默认关闭）；`DisconnectAsync` 之后不会连回；请求不会隐式连接。
- 只提供异步 API，不做同步双轨。`RetryCount` 默认 0（2.x 为 3）。
- **原因**：与其他协议一致，消除设计 11.2 的差异。

### DI 与创建入口（P7-D14）

- `ModbusClientConfig`（`Transport`、`Tcp`、`Udp`、`Serial`、`Options`），`AddModbus()` 注册创建器；替代 2.x 的 `IModbusFactory` 与 `AddModbusFactory()`。

### 功能范围（P7-D1、P7-D15）

- 功能码 01–06、0F、10、16、17；0x16 与 0x17 经 S2 发送，享有操作锁、重试与错误归类。
- 诊断、文件记录、FIFO、设备标识、广播不做。

### 已知不确定项（P7-D17）

- 与设备替身联调，未对真实设备验证；详见 [[协议细节/Modbus 协议]] 的未验证清单。

### 实施中的修订（计划第 25.2 节）

- 套件测试的并行不稳定：S2 的串行顺序测试阻塞了线程池线程，改用 `GatedClientChannel`（异步保持应答），变异检查仍能发现缺失的锁。
- 请求超时重建连接与紧接着的重试竞争：P7 期间只记录；随后在通道层修复（设计文档 20.1 第 43 项，2026-10-19 通道修复），影响所有 Sequential 加 `ResetOnRequestTimeout` 的字节流客户端（S7、FINS、TCP 上的 MELSEC、RTU over TCP），不只 Modbus。
- 审阅者对开放决策的结论（P7 第一轮验收，2026-10-20）：F-A1 不扩展套件（两个自写解析器语法差别很大，没有第三个使用者）；F-A2 把 `IClientChannel` 脚本替身移入共享测试库（`ScriptedClientChannel`）；F-A3 的 `DelayingStream` 留在 Modbus.Tests；RTU 分帧器对噪声重新同步、不抛异常（R1）。
