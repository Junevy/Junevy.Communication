## 目标与前提

P5.1 已经把通信层做完：SECS-II 消息模型、HSMS-SS 会话（Select / Linktest / 单会话 / 两种连接模式）、设备端派发与 S9 应答，见 [[协议细节/SECS-II 与 HSMS]]。**P5.2 只在它上面加 GEM 的设备端语义**，不重写通信层，也不把它塞进 `Plc` 套件（GEM 不是地址型协议）。

设计文档第 14.1 节写了"SECS 对外暴露 GEM 的通讯状态与控制状态"，但没有列举具体能力；SEMI E30 的 GEM 标准原文仓库里没有，和 P5.1 一样要靠公开资料逐字段核对。

## 开工前必须向用户确认的问题

1. **能力清单做到哪一层。** GEM 的设备端能力至少有：通讯状态机（`ENABLED` / `NOT COMMUNICATING` / `WAITING FOR CRA`）、控制状态机（`OFFLINE` / `ATTEMPTING ON-LINE` / `ON-LINE`）、`S1F1`/`S1F2`（已上线）、`S1F13`/`S1F14`（建立通讯）、`S1F15`/`S1F16`、`S1F17`/`S1F18`（心跳）、`S5F1`/`S5F2`（报警报告）、`S5F3`/`S5F4`（已清报警）、`S5F5`/`S5F6`（报警列表）、`S6F1`/`S6F2`（远程命令）、`S7F1`/`S7F2` 等数据收集、`S9Fx` 之外的 `S6F11`/`S6F12`（事件报告）。**问题是：全做，还是先做通讯状态 + 控制状态 + 报警（`S5Fx`）这一组？** 全做的状态机耦合与测试量是本期的数倍。
2. **状态放在哪一层。** 通信状态与会话状态（`HsmsState`）是两回事：`HsmsState.Selected` 只说明 HSMS 会话可用，GEM 的 `ON-LINE` 还需要通讯状态为 `ENABLED` 且主机完成 `S1F13`。是新增 `GemState`（公开）并在 `HsmsEquipment` 之上再包一层 `GemEquipment`，还是在 `HsmsEquipment` 上挂事件由宿主自己聚合？前者边界清楚但多一个公开类型，后者少一个类型但把状态机分散到宿主。
3. **控制命令（`S6F1`）的默认安全策略。** 远程命令会改设备动作。库是否内置白名单 / 参数范围校验，还是只把 `S6F1` 交给宿主处理器、由宿主保证安全？P5.1 的原则是"库不替宿主猜"，这一点要明确写进 README。
4. **是否需要 `JIS` 与 `C2` 数据项。** P5.1 明确不支持（解码按非法数据处理）。现场若真用到 JIS-8 文本（`J`）或双字节字符（`C2`），P5.2 之前就得决定是补解码还是由宿主转码后用 `B`。
5. **未经真机验证的策略。** P5.1 的做法是 README 末尾一条未验证清单（P51-D18）。GEM 的状态机与事件序列同样没有真机，需要提前确认用户接受同样的验收口径。
