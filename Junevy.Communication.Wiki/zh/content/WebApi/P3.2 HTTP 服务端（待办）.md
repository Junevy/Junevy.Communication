## 目标

P3 的完整目标是"MES 能向通讯库下发，通讯库也能主动上报 MES"。主动上报已由 P3.1 完成（[[WebApi/WebApi 客户端与钩子]]），本项补上**接收 MES 下发**：在 `Junevy.Communication.WebApi` 中提供 HTTP 服务端，命名空间 `Junevy.Communication.WebApi.Server`。

用户 2026-10-11 的要求同样适用于服务端：预留按阶段挂接逻辑的钩子，事件用于旁观，中间件用于干预，与客户端的"事件 + 拦截器"同一模型。

## 设计文档已定的内容（第 15.5 节）

- 接口 `IWebApiServer`：`StartAsync` / `StopAsync`、状态与状态事件；`MapGet` / `MapPost` 注册路由，必须在 `StartAsync` 之前。
- 配置 `WebApiServerConfig` 的默认值：
  - `Prefixes` 为 `http://+:8080/`。
  - `MaxConcurrentRequests` 16，超出返回 503。
  - `RequestTimeout` 30000 ms，处理器超时返回 504。
  - `MaxRequestBodySize` 1 MiB，超出返回 413。
  - 另有 `Envelope`、`RestartOnFault`、`LogBodies`。
- 标准错误响应：404、405、401、400、413、500、503、504。500 只返回通用消息，异常详情只写日志。
- 处理器在线程池上并发执行，线程安全由宿主负责。
- 不用 Kestrel：它不支持 net472，还要求宿主引用 ASP.NET Core 共享框架。

## P3.1 已经为它准备好的部分

- `ResponseEnvelopeOptions` 位于根命名空间，客户端和服务端共用。
- `Serialization` 中的 `ResponseEnvelopeCodec` 目前只有"读"。服务端需要加"写"，结构上不需要改动。
- `IWebApiSerializer` 位于根命名空间，服务端可以直接用它序列化请求与响应。
- 事件参数：`WebApiCallEventArgs` 只服务客户端。服务端事件另设基类，不复用客户端的 `CallId` 语义（P3.1 计划第 17 节）。
- 架构测试 `WebApiLayeringTests` 的分层表要加 `Server` 一行。预期依赖：根、`Serialization`、`Auth`；不得依赖 `Http`（客户端管线）、`Rest`、`Soap`。
- 可复用的同类实现：Core 的 `EventSubscribers.InvokeEach`（逐订阅者派发），以及 `Http/OrderedEventQueue` 的有序状态事件做法。

## 开工前必须向用户确认的问题

1. **监听实现。** 设计文档定的是 `HttpListener`，部署时有三个陷阱：
   - 非管理员账户运行，需要先执行 `netsh http add urlacl url=http://+:8080/ user=<运行账户>`。
   - HTTPS 需要用 `netsh http add sslcert` 绑定证书。
   - 防火墙要放行端口。
   如果现场无法做这些配置，需要另选方案。注意 WebApi 只依赖 Core，不能直接复用 `Junevy.Communication.Tcp` 的 `TcpServer`。
2. **状态与重启类型放在哪里。** 设计 15.5 引用的 `ServerState`、`ServerStateChangedEventArgs` 在 Tcp 包，`ReconnectOptions` 在 Channels 包，WebApi 都引用不到。可选两种做法：WebApi 自建同名类型，或把通用部分移入 Core（需要动 Tcp 和 Channels，按"行为不变"的规则做）。
3. **服务端钩子的具体形态。**
   - 中间件（干预）：认证、审计、改写响应等，在路由处理器之前或之后执行。
   - 事件（旁观）：例如收到请求、请求被拒（401/404/413/503 等）、处理器异常、响应已发出。
4. **服务端认证。** 设计 15.2 预留了 `IRequestAuthenticator`，内置 Basic / Bearer / ApiKey 校验。凭据规则与客户端一致，只能来自环境变量或代码注入。
