## 重试规则（`RetryPlanner`）

1. **结果规则**：只有 `ConnectionClosed`、`Timeout`，或状态码为 408 / 429 / 500 / 502 / 503 / 504 的结果可重试；**带 `RemoteCode` 的永不重试**（业务包络失败码、SOAP Fault 说明请求已到业务层）。`ProtocolViolation`、`InvalidRequest`、`Unspecified`、`Cancelled` 不重试。
2. **方法规则**：GET / HEAD / OPTIONS 自动可重试；POST / PUT / PATCH / DELETE 只有调用带 `IdempotencyKey`，或配置 `RetryUnsafeMethods = true` 才重试（比 RFC 9110 保守：重复上报会让过站与产量重复计数）。
3. **次数**：`RetryCount`（默认 0）；退避为固定的 `RetryDelay`（默认 1000 ms）或 `WebApiComponents.RetryBackoff`（`IBackoffPolicy`，返回 null 表示放弃）。
4. **`Retry-After`**：仅对 429 / 503，秒数或 HTTP 日期，只能把等待拉长；超过 30000 ms 则不重试。
5. **拦截器重放**：`RequestReplay` 每次调用最多 1 次，立即重发，不计入 `RetryCount`，不受方法规则限制；`Fail`、抛异常、改来源造成的结束一律不重试。重放之后再收到可重试的结果，仍按上述规则重试。
6. **取消**：退避期间调用方取消 → `Cancelled`，不再发送；释放 → `ConnectionClosed`，不再重试（`AttemptLoop.MapDisposal`）。
7. **事件**：每个已发出的尝试触发 `ResponseReceived`（`WillRetry`、`RetryDelay`）；没有发出的尝试（拦截器中止、`OnSendingAsync` 内超时）没有该事件，`OnSendingAsync` 内的超时仍按"尝试超时"可重试。

## 可用性（`AvailabilityTracker`）

- 初始 `Unknown`。传输层结果计为**失败**：`ConnectionClosed`、`Timeout`、HTTP 502 / 503 / 504；收到其他任何响应（含 4xx、业务错误、超限响应）→ `Online` 并清零；连续 `OfflineThreshold`（默认 3，≥ 1）次失败 → `Offline`。`Cancelled` 与 `InvalidRequest` 既不计数也不清零；没有发出的尝试不报告。
- `AvailabilityChanged` 的 `Reason`：导致 `Offline` 的最后一次失败的分类（502/503/504 按状态码归类为 `RemoteError`），其余为 `None`；`Exception` 为该次失败的异常。
- 状态变化在锁内入队、由 `OrderedEventQueue` 的单消费者按顺序触发（并发请求与健康检查同时改变状态时事件不会乱序）；每次变化记 Information 日志。
- **健康检查**（REST `HealthCheckPath`、SOAP `HealthCheckUrl`，后者必须与 `Url` 同源）：**构造后立即开始**，每 `HealthCheckInterval`（默认 30000 ms）一次 GET，经拦截器链与超时，不重试，不触发请求事件，调用序号固定为 0；任何 HTTP 应答都说明可达。因为在构造时就开始，订阅者可能错过第一次变化：**先订阅，再读一次 `Availability`**。

## 释放

`Dispose` / `DisposeAsync` 幂等：置已释放标志 → 取消在途调用 → 停止健康检查 → 等待可用性事件队列派发完（`DisposeDrainMilliseconds = 2000`，剩余事件丢弃并记 Warning）→ 释放自己创建的 `HttpClient` 与处理器（注入的 `HttpHandler` 不释放）。同步 `Dispose` 最多等 `2000 + 1000` ms（沿用 `SupervisedChannelCore` 的先例，超时记 Warning）；在 `AvailabilityChanged` 处理器内调用时不等待自己（`OrderedEventQueue.IsDispatching`）。之后的调用返回 `NotConnected` 且不触发事件。
