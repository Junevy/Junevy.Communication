## SocketTimingCollection —— 并行隔离（2026-10-08 P2 引入，必须遵守）

```csharp
[Collection(SocketTimingCollection.Name)]   // 定义见 SocketTimingCollection.cs
public class XxxTests { ... }
```

**规则：新增任何"建立真实套接字"或"断言毫秒级墙钟预算"的测试类，都必须加 `[Collection(SocketTimingCollection.Name)]`。**（通道族的各测试项目适用同一规则，见上文"通道族测试"。）

原因：这些用例会新建大量套接字（`DisposeConcurrencyTests` 单轮测试就循环 20 次、累计数百个），若与其它用例并行，线程池调度延迟会让毫秒预算断言偶发失败——2026-10-08 实测出现过三类误报：

| 误报用例 | 现象 | 根因 |
|---|---|---|
| `TransportBaseRetryTests.TcpClient_DefaultConfig_ServerNeverReplies_SendsExactlyOneRequest` | `Expected single-attempt return, took 2041ms`（预算 1200ms，ReadTimeout=300） | 300ms 定时器的续体被推迟 1.7s |
| `ConnectAsyncTokenTests.ConnectAsync_CancelledDuringOpen_Throws` | 100ms 取消耗时超 1500ms | 同上 |
| `ModbusProtocolTests.TcpClient_ExceptionResponse_IsTerminal_NoRetry` | 请求数 2 ≠ 1 | 服务端与客户端重连时机错位 |

xUnit 保证同一集合内的类串行执行，因此把这些类集中到一个集合既消除互相干扰，又不影响纯内存单元测试之间的并行。**修正后全量连跑 6 次全绿，上述三个用例不再出现偶发。**

新增测试类时的对照：纯内存的单元测试（解析器、扩展方法、工厂校验）**不要**加，会白白损失并行度。

## 已知偶发用例

> 以下 Modbus 的条目属于 2.x（对应测试已删除）。3.0 的 Modbus 测试在 P7 Task 15 的三遍运行中全部通过。

P2 之前全量并行下偶发（`TcpClient_ExceptionResponse_IsTerminal_NoRetry`，Expected 1 / Actual 2）。**引入 `SocketTimingCollection` 后已不再复现**；若再次出现，先确认新类是否漏加集合标记。

判定规则：该用例之外有失败 → 必须修复；仅该用例失败 → 单独重跑，通过即记为已知偶发，不阻塞提交。

判定规则：该用例之外有失败 → 必须修复；仅该用例失败 → 单独重跑，通过即记为已知偶发，不阻塞提交。

**曾被误判为偶发的 SECS 主动端用例（2026-10-14）**：合并后的全量并行里，`HsmsEquipmentActiveTests` 的主动端用例在 net8.0 上 9 遍失败 6 遍（"状态迟迟不进 `NotSelected`"或"设备端发的 S5F1 主机收不到"），单独运行从不出现。一度按本节规则当作高负载偶发处理并放宽了等待，放宽到 10 秒后照样失败——**不是慢，是真缺陷**：通道的状态事件排队送达，晚到的 `Connecting` 把会话状态复位了（详见 [[协议细节/SECS-II 与 HSMS]] 的"状态从哪里来"）。修复后等待恢复原值。**教训**：同一条用例反复只在全量下失败时，先加诊断看日志，不要先放宽超时；"放宽之后还失败"本身就说明不是计时问题。

## Category=Network 测试（2026-10-07 P2 新增）

P2 起有一组用例访问不可路由地址 `10.255.255.1`（验证 `ConnectTimeout` 生效），统一标记 `[Trait("Category", "Network")]`：

```bash
dotnet test --filter "Category!=Network"    # 排除该组
```

排除的理由是**环境相关**：某些网络环境对不可路由地址立即返回"网络不可达"，单次连接尝试 <300ms 就失败，此时这些用例失去判定能力（`Connect_UnroutableAddress_RespectsConnectTimeout` 断言耗时 ≥450ms）。本仓库当前环境实测该地址会挂起满 `ConnectTimeout`，判定能力正常，6 个 `TcpConnectTests` 全部通过（含 Network 组 2 个）。换环境后如遇立即不可达，按上述命令排除并在合并请求中注明。

| 组件 | 作用 | 用法要点 |
|---|---|---|
| `Polling.WaitUntilAsync(Func<bool>, int ms = 10000)` | 轮询直到条件成立或超时 | 5 ms 间隔。**超时抛异常之前仍做最后一次判定**，所以"最后一刻才变 true"不会误判。不要再写 `Thread.Sleep` 轮询循环 |
| `Arrival.WithinAsync(Task<T>, int ms)` / `WithinAsync(Task, int ms)` | 等某个任务在时限内到达，超时即让测试失败 | 取代各测试自写的 `Task.WhenAny` + `Task.Delay` 竞态 |
| `LoopbackTcp.Client(port)` / `Reconnecting(port, …)` / `WithHeartbeat(port, …)` | 回环地址 `127.0.0.1` 上最小可用的 `TcpClientChannelConfig`：只有端口、再加重连、再加心跳与重连。三个是各自独立的静态工厂（不能链式调用），每次返回新对象，用例可以继续修改 | 端到端故障用例的重连/心跳装配。`TcpClientChannel` 在构造期就校验端口，所以"只验证 `Create` 守卫"的用例也要用它拿一个合法端口 |
| `PlcByteMemory` + `PlcByteAccess` | 按 `(区名, 块号)` 分块的**线程安全**字节存储 | `Define(area, block, length)` 建全 0 块并返回存储；`Block(area, block)` 取出来预置与核对；`TryRead` / `TryWrite` 返回 `Ok` / `NoSuchBlock` / `BeyondEnd`，**写失败时块一个字节都不变**。把后两种翻译成协议自己的错误码是替身的活 |
| `PlcMemory`（P1 已有） | 字粒度存储 | **没有被改成 `PlcByteMemory` 的视图**——两者并存：字粒度用 `PlcMemory`，字节粒度用 `PlcByteMemory`。理由见 [[测试/P4.6 测试基建整理（已完成）]] |

`Junevy.Communication.Testing` 因为 `LoopbackTcp` 需要 `TcpClientChannelConfig`，从 P4.6 起还引用了 `Junevy.Communication.Tcp` 项目。它仍是 `IsPackable=false` 的测试库，架构测试只约束生产程序集。

## 测试范围：只跑受影响的项目（2026-10-13 起）

全量（24 个测试宿主、约 5600 条）不再是每个 Task 的门槛。Core、Channels 等没有改动的包，测试已经跑过很多遍；每次只跑与本次改动有关的测试项目，由 `build/test-affected.ps1` 选：

```powershell
pwsh build/test-affected.ps1 -Base <起点提交> -NoBuild             # 每个 Task：一遍
pwsh build/test-affected.ps1 -Base <起点提交> -NoBuild -Repeat 3   # 期末与审阅复跑：三遍
pwsh build/test-affected.ps1 -Base <起点提交> -ListOnly            # 只看会选中哪些项目
```

- **改动**：`-Base` 与 HEAD 的分叉点之后的提交，加上工作区里未提交、未跟踪的文件。`-Base` 用计划 Task 0 开始时的 HEAD；不要用 master，否则分支上前几期的改动也会算进来。
- **选法**：每个改动文件归到它所在的项目，再沿 `ProjectReference` 选出直接或间接引用该项目的测试项目。Architecture.Tests 引用全部生产程序集，因此改任何生产项目都会带上它；只改某个测试项目时只跑它自己。
- **不触发测试**：项目目录以外的文档与脚本（`*.md`、`docs/`、知识库、`Skills/`、`build/*.ps1`、`build/metrics/`），以及解决方案文件（新增项目由它自己的目录归属）。包目录里的 `README.md` 属于该项目，会触发它的测试（README 示例有逐字比对的用例）。
- **自动跑全部**：项目目录以外的共享构建输入改动时，例如 `build/` 下的 props、app.config、Polyfills。
- **会把范围扩大到接近全量的改动**：Core（所有包都引用它）；共享测试库 `Junevy.Communication.Testing`（除 Architecture 外的全部测试项目都引用它，包括 P7 后的 Modbus 测试项目）；Channels 与 Tcp（Testing 引用它们）。因此新协议专用的测试替身放在自己的测试项目里，确实要共用时才放进 Testing。
- **构建不缩小**：`dotnet build Junevy.Communication.slnx -c Debug` 与 `-c Release` 仍然构建整个解决方案。增量构建很快，也由它发现解决方案层面的构建问题。
- **合并进 master 之后**：以两个分支的分叉点为 Base 跑一遍，覆盖两边改动的交叉影响。合并提交用 `-Base (git merge-base HEAD^1 HEAD^2)`；快进合并用合并前的 master 提交。
- 用户要求或排查环境问题时，加 `-All` 跑整个解决方案。
- 设置了 `JUNEVY_SERIAL_PAIR` 时，脚本逐个项目运行，Serial.Tests 与 Melsec.Tests 不会同时占用端口；`-All` 仍按整个解决方案并行运行，这时照 [[Agent协作/开发约定与验收基线]] 的要求把这两个项目单独逐个运行。

脚本退出码：全部通过为 0，任一测试宿主失败为 1，失败时打印该项目的完整输出。2026-10-13 实测：只改 Mqtt 时选中 Architecture.Tests 与 Mqtt.Tests（3 个测试宿主、262 条）；加一条必失败的临时用例时退出码为 1，并列出该用例。
