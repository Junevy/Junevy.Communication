# 架构扩展性评估（以 P2 的 MELSEC 为样本，2026-10-11）

问题：① 在当前架构上新增一个通信组件有多复杂？② 反过来看，架构需不需要调整？
依据：P2 的实测度量（计划 `docs/superpowers/plans/2026-10-11-p2-plc-melsec.md` 第 20.3 节，审阅者独立复核）、执行中记录的 13 条扩展性摩擦（同计划第 20.2 节）、P1 代码质量补审（`2026-10-11-p1-code-quality-audit.md`）。

## 1. 结论

- **分层与协议族的划分经受住了检验，不需要调整。** MELSEC 从地址表到 DI 全部写在自己的包里，Core / Channels / Plc / Tcp / Udp / Serial 的生产代码一行未改；协议对套件的"差异接口"只有 11 个覆写、共 27 行。
- **需要调整的是"接缝"，不是"分层"。** 13 条摩擦里有 8 条指向同一个根因：Channels 的公开扩展面比它的内部能力薄。P1 的 Tcp / Udp 通过 `InternalsVisibleTo` 使用内部类型，掩盖了这些缺口；Plc 与 Melsec 是第一批"只能用公开 API"的使用者，于是全部撞上。
- **建议在 P4（S7、FINS，Plc 套件的第二、第三个使用者）之前做一次"接缝整理"**（第 4 节，约等于一个里程碑的工作量）。P3 WebApi 只依赖 Core，不受影响，可以并行。

## 2. 新增一个通信组件的复杂度（实测）

### 2.1 MELSEC 写了什么

| 部分 | 有效行 | 占比 | 性质 |
|---|---:|---:|---|
| 协议层 `Protocol/`（3E / 4E / 4C × 二进制 / ASCII、DLE 转义、和校验、请求体） | 784 | 60% | 协议固有知识，任何架构下都要写 |
| 客户端（`McClient` + 钩子 + 设置） | 253 | 19% | 其中 11 个钩子 27 行；三个传输工厂方法约 90 行（见 3.3） |
| 分帧与关联（`Framing/`） | 110 | 8% | 声明为主；4C 格式 5 需要自定义分帧器（见 3.1） |
| 配置与地址（含 28 行声明式软元件表） | 101 | 8% | 声明为主 |
| 依赖注入 | 56 | 4% | 样板 |
| **合计** | **1304** | | 38 个文件 |

### 2.2 MELSEC 没写、但自动获得的

连接与重连、心跳调度（MELSEC 只提供 0619 探测）、超时、粘包半包、请求串行化、4E 迟到应答丢弃（Keyed 关联）、重试、拆包、字中位读取与读-改-写、8 种数值类型 + 字符串 + 位的类型化读写、字节序转换、日志、命名注册表、DI 骨架、TCP / UDP / 串口三种接法，以及测试用的设备模拟器底座。对应的共享代码：Plc 1054 行、Channels 约 7700 行、三个传输包约 5000 行。

### 2.3 复杂度判断

- **协议作者的工作量 ≈ 协议本身的复杂度。** 60% 是不可约的协议知识；去掉它，"接入成本"约 520 行，其中真正需要理解套件契约的只有钩子（27 行）与传输声明（110 行）。
- **对后续协议的估计**（参考，非承诺）：S7（TPKT / COTP + S7 PDU，单一编码，需要握手与 PDU 协商）约 900–1200 行；FINS（TCP 握手 + UDP，单一编码）约 700–1000 行。主要工作量都在各自的帧编码。
- **偏差提醒：** MELSEC 是套件的设计基准，套件按它的形状设计，单一样本会高估通用性。S7 的字节地址（`PlcAddressUnit.Byte`）与运行期协商的上限是真正的第二次检验，P4 应把它当作验证项。

## 3. 摩擦归类（13 条，原文见计划第 20.2 节）

### 3.1 Channels 的公开扩展面不足（8 条，根因相同）

| 现象 | 影响 |
|---|---|
| `ConnectionStatistics`、`ConnectionStateChangedEventArgs` 的构造函数为 internal | Channels 之外无法实现 `IClientChannel`（自定义通道、测试替身只能用反射） |
| 自定义 `IFrameCodecFactory` 拿不到 `MaxFrameLength`；透传编码器是 internal | 格式 5 分帧器自带帧长上限、借用 Raw 工厂取编码器 |
| 没有前进式字节读取器 | 自定义分帧器复制窗口、每次到达重新扫描 |
| 没有公共的缓冲写入器与 `IBufferWriter` 写入扩展 | 代码库中已有第三份手写实现 |
| 组件静默覆盖传输配置中的同名设置 | MELSEC 只能用"与默认实例比较"来拒绝 |
| 配置只在通道构造时校验，没有公开的 `Validate()` | 创建器无法预检，异常类型不一致 |
| 协议客户端无法核对通道是否按协议配置 | `McClient(IClientChannel, …)` 只能靠文档约束调用方 |
| 测试辅助（分段序列）是测试项目内部类型 | 已在 P2 移入 Testing |

### 3.2 Plc 套件契约的小缺口（2 条）

- `PlcAddress.Device` 是接口类型，协议地址用 `new` 隐藏并向下转换。
- 构建钩子返回 `void`，不能报告"协议不可表示"；P2 用 `ValidateRange` 两段式解决，**可以接受，不建议改契约**。

### 3.3 跨协议会重复的样板（审阅者观察）

- 每个协议都要写 `CreateTcp` / `CreateUdp` / `CreateSerial`（MELSEC 约 90 行），逻辑相同：校验传输配置 → 用协议配置填组件 → 构造对应通道。P1 已经有按配置类型创建通道的抽象 `IChannelCreator`，套件可以复用它，协议只需一个 `Create(IChannelConfig transport, …)`，以后新增传输（例如带 TLS 的变体）时协议包不用改。
- `PlcClientFactory` 与 `ChannelFactory` 的外壳重复约 83 行；以后 SECS 等协议族也会需要同样的工厂。

### 3.4 P1 内部的重复与过大类型（来自补审，影响维护而非扩展）

字节流 / 数据报三层平行复制（约 500 行）、`TcpServer` 1216 行、生产代码中的测试钩子。

## 4. 反向评估：要不要调整架构

### 4.1 保持不变

- 协议族划分（字节通道族 / 地址型设备族 / SECS / SDK 协议 / 无状态请求）与依赖方向（协议 → 套件 → 通道 → Core）。
- 协议客户端**持有**通道（组合），套件用模板方法收集协议差异。
- Core 只放无语义工具；WebApi、OPC UA 等不依赖 Channels。
- 不建议新增抽象层，也不建议合并包。

### 4.2 建议的调整（按优先级）

| # | 调整 | 解决 | 范围 |
|---|---|---|---|
| A1 | **Channels 公开扩展面补齐**：可构造的连接统计（或抽象）、公开透传编码器与分帧上下文（含 `MaxFrameLength`）、基于 `SequenceReader<T>` 的前进式扫描辅助、配置的公开 `Validate()`、组件与配置的优先级显式化（组件覆盖非默认配置时拒绝或记录） | 3.1 的 7 条 | Channels（公开 API 增量，非破坏性） |
| A2 | **以"不靠 `InternalsVisibleTo`"为验收规则**：生产程序集之间不再新增 IVT；Tcp / Udp 现有的 IVT 逐步替换为公开 API | 防止 3.1 再次被掩盖 | Channels、Tcp、Udp |
| A3 | **Core 增加公开的缓冲写入器与 `IBufferWriter` 扩展**，三份手写实现合并 | 3.1、补审第 19 节 | Core、Channels、Plc、Testing |
| A4 | **Plc 提供通用的传输绑定**：基于 `IChannelCreator` 的 `Create(IChannelConfig transport, …)`，协议只声明组件 | 3.3 第一条 | Plc（不引用传输包，依赖方向不变） |
| A5 | **工厂外壳上移到 Core**（命名注册 + 按配置类型选择创建器的泛型基类），`ChannelFactory` 与 `PlcClientFactory` 共用 | 3.3 第二条 | Core、Channels、Plc |
| A6 | **P1 内部去重与拆分**：字节流 / 数据报共享请求协调、停止序列、握手执行；`TcpServer` 按监听 / 接入 / 握手 / 事件派发拆分；去掉测试钩子 | 3.4 | Channels、Tcp（行为不变） |
| A7 | 可选：泛型地址基类 `PlcAddress<TDevice>` | 3.2 第一条 | Plc（P4 时随 S7 一起评估） |

### 4.3 建议的顺序

1. **P2.5 接缝整理**（A1–A6，行为不变的重构 + 公开 API 增量）：在 P4 之前完成。理由：S7 / FINS 会以同样的方式撞上 3.1 的缺口（自定义分帧、测试替身），越晚做返工越多；P1 补审的重复也在同一批文件里，一起做成本最低。验收指标：重复块扫描与超长方法数下降、P1 + P2 全部测试不变、Melsec 的三个工厂方法被 A4 取代后有效行减少。
2. **P3 WebApi** 可与 P2.5 并行（只依赖 Core）。
3. **P4 S7 / FINS** 时把 A7 与 `PlcAddressUnit.Byte` 作为验证项，并继续记录摩擦。
