### 0.2 P6.1 决策

| # | 决策 | 理由 |
|---|---|---|
| P61-D1 | 新增库 `Junevy.Communication.Mqtt`（依赖 Core + MQTTnet）和测试项目 `Tests/Junevy.Communication.Mqtt.Tests`（另加 MQTTnet.Server）。<br>命名空间：<br>• `Junevy.Communication.Mqtt`：客户端、消息、选项、枚举、事件参数；<br>• `Junevy.Communication.Mqtt.DependencyInjection`；<br>• `Junevy.Communication.Mqtt.Sdk`：内部，P6-C5。<br>生产项目只对测试项目开放 IVT | 设计 3.1；P6-C1、C5 |
| P61-D2 | 协议版本：MQTT 3.1.1（默认）与 5.0（选项）；不支持 3.1 | 3.1.1 是现场 Broker 普遍支持的版本 |
| P61-D3 | 消息模型 `MqttMessage`：<br>• 不可变，构造时**复制**正文；收到的消息同样复制正文后才交给宿主（SDK 的缓冲区可能被复用）；<br>• MQTT 5 属性（ContentType、ResponseTopic、CorrelationData、MessageExpiryInterval、UserProperties）用 `init` 设置，设置时复制；<br>• 在 3.1.1 连接上发布带有任何 MQTT 5 属性的消息，返回 `InvalidRequest`，不发送。**不静默丢弃** | 用户选择纳入 MQTT 5 扩展属性；静默丢弃属性会让宿主误以为发出去了 |
| P61-D4 | 连接：<br>• `ConnectAsync` 只在 `Disconnected` 时连接；已是 `Connected` 时直接返回成功；`Connecting` 或 `Reconnecting` 时返回 `InvalidRequest`（"A connection attempt is already in progress."）；<br>• `CleanSession` 对应 3.1.1 的 Clean Session 和 5.0 的 Clean Start；<br>• `SessionExpiryInterval`（秒）只在 5.0 下可以非零；<br>• `KeepAliveSeconds` 交给 SDK 发 PINGREQ；<br>• `Timeout` 同时用作连接超时和每个需要确认的报文的等待时间；<br>• 有密码就必须有用户名（3.1.1 的规定）；<br>• TLS：`UseTls` 与 `AllowUntrustedCertificates`。后者为 true 时接受任何证书和主机名不符，`Create` 时记一条 Warning | MQTT 原生语义；TLS 失败按 Tcp 的先例归为 `AuthenticationFailed` |
| P61-D5 | 状态：`MqttConnectionState { Disconnected, Connecting, Connected, Reconnecting }`，经 `StateChanged` 按发生顺序通知，状态只在一个地方变化（Q35 照用）。重连成功并**恢复完订阅之后**才进入 `Connected` | 宿主看到 `Connected` 时，订阅已经可用 |
| P61-D6 | 发布：<br>• QoS 0 写出即成功；QoS 1 收到 PUBACK 成功；QoS 2 收到 PUBCOMP 成功；确认的原因码 ≥ 0x80 时失败（第 15 节）；<br>• 不是 `Connected` 时返回 `NotConnected`；<br>• 发布过程中断线返回 `ConnectionClosed`，**不自动重发**（Broker 是否已收到未知，由宿主决定）；<br>• 主题为空或含 `+`、`#` 时返回 `InvalidRequest`。主题与过滤器的合法性交给 SDK 校验，SDK 抛出的校验异常映射为 `InvalidRequest`，不自己再写一份校验 | 设计第 22 节：不提供离线队列；避免重复造轮子 |
| P61-D7 | 订阅：<br>• `SubscribeAsync(filter, qos)` 一次一个过滤器，返回 Broker 授予的 QoS；<br>• 成功的订阅记入订阅表（过滤器 → 请求的 QoS）。同一过滤器再订阅时更新 QoS，Broker 拒绝的不记录；<br>• `UnsubscribeAsync` 成功后才从表中移除；<br>• 不是 `Connected` 时两者都返回 `NotConnected`，订阅表不变 | 订阅表是重连后恢复订阅的唯一依据 |
| P61-D8 | 接收：<br>• 在 SDK 的接收回调里同步触发 `MessageReceived`，用 Core 的 `EventSubscribers.InvokeEach`，单个订阅者抛异常只记 Error；<br>• 订阅者都返回后 SDK 才发 QoS 确认（SDK 的自动确认），因此同一连接上的消息按到达顺序逐条交付；<br>• README 写明订阅者不能阻塞，否则会拖住后续消息和确认 | 保持 QoS 1 / 2 "交付给宿主后才确认"的语义；不引入额外队列 |
| P61-D9 | 重连（`AutoReconnect` 为 true 时）：<br>• **触发**：SDK 报告"原本已连接、并非我方主动断开"的断线 → 状态转 `Reconnecting`（`Reason` 取 SDK 给出的原因），在后台任务里启动重连循环（不在 SDK 的事件回调里重连，SDK 示例明确警告这样会死锁）；<br>• **退避**：Core 的 `ExponentialBackoff(ReconnectInterval, MaxReconnectInterval, 2.0, 0.2, 0)`，不限次数，每次尝试前先等待；<br>• **成功**：如果 Broker 回的 Session Present 为 false，按订阅表**逐个**重新订阅（某个过滤器失败只记 Warning，并把它移出订阅表），然后转 `Connected`；Session Present 为 true 时不重新订阅（避免 Broker 重发保留消息）；<br>• **失败**：记 Warning（尝试次数、错误分类）后继续；认证失败也继续重试（Broker 侧的凭据可能被修正）；<br>• **停止**：`DisconnectAsync` 或释放时停止，并等待循环退出；<br>• `AutoReconnect` 为 false 时，断线直接转 `Disconnected`。<br>不在 Core 新增 `RetryLoop`：这是带状态迁移和恢复订阅的后台循环，不是通用的"重试一个操作"（P2-D3 的规则） | P6-C11；设计 14.3："重连成功后自动重订阅" |
| P61-D10 | 并发：<br>• SDK 要求连接、断开不能与其他操作并发，因此生命周期操作（连接、断开、每一次重连尝试）用同一把异步锁串行；<br>• 发布、订阅、退订先检查状态再调用 SDK，可以并发（SDK 保证线程安全）；<br>• 断线与这些操作竞争时，SDK 抛出的异常按第 15 节映射为 `ConnectionClosed` 或 `NotConnected`，不能出现未观察的任务异常 | MQTTnet `IMqttClient` 的线程安全说明 |
| P61-D11 | 释放：停止重连循环 → 已连接时尽力发 DISCONNECT（不等待超过 `Timeout`）→ 释放 SDK 客户端；之后状态为 `Disconnected`，P6-C8 的释放规则适用 | 与 P5.1 的 `StopAsync` 一致 |
| P61-D12 | 依赖注入：`MqttClientFactory`（`NamedFactory<MqttClient>`，`GetOrAdd(name, options)`）与 `MqttServiceCollectionExtensions.AddMqttClients()` | P6-C9 |
| P61-D13 | 已知不确定项，写进 README 的"Verification status"：<br>① 只与进程内的 MQTTnet.Server 联调过，没有对 Mosquitto、EMQX、HiveMQ 等真实 Broker 验证；<br>② Session Present 为 true 时不重新订阅，依赖 Broker 正确保存会话；<br>③ 订阅者阻塞会拖住确认 | 诚实记录 |
| P61-D14 | 遗嘱消息（Last Will）：<br>• 选项给出 `WillTopic` 时，每次连接（含重连）都在 CONNECT 中携带遗嘱；<br>• 正文是 UTF-8 文本，因为选项要能从 appsettings 绑定；<br>• 遗嘱只在**异常断开**时由 Broker 发布。`DisconnectAsync` 与释放会发 DISCONNECT，按 MQTT 的规定 Broker 会丢弃遗嘱，README 写明；<br>• 常见用法写进 README：`WillTopic = "devices/{id}/status"`、`WillPayload = "offline"`、`WillRetain = true`，连接成功后由宿主自己发布一条保留的 `online`。库不自动发布上线消息 | 用户 2026-10-12 追加；设备在线状态的标准做法 |

## 1. 执行规则（每个 Task 都适用）

1. 每个 Task 一个提交，在 `feat/sdk-p6` 上提交。不 push、不 amend、不 rebase、不切换分支。**只 `git add` 本 Task 的文件。**知识库只在 Task 9 回写，**不提交**；汇报时附上 `git status --short -- Junevy.Communication.Wiki` 与 `git diff --stat -- Junevy.Communication.Wiki` 的输出。
2. 步骤顺序固定：**先写测试并确认失败**（新代码阶段无法编译也算失败）→ 写生产代码 → 测试通过 → 按第 2 节自查并清理 → 更新文档 → 提交。
3. 每个 Task 完成后依次运行，全部成功才能提交：
   ```bash
   dotnet build Junevy.Communication.slnx -c Debug
   dotnet build Junevy.Communication.slnx -c Release
   dotnet test Junevy.Communication.slnx -c Debug
   ```
   - 已有测试项目在 net8.0 与 net472 上各运行一次（Modbus 只有 net8.0）；Mqtt 测试只有 net8.0（P6-C1）。
   - 测试宿主因内存紧张崩溃时，先运行 `dotnet build-server shutdown` 再重跑。
   - 已知的偶发计时失败：Channels 的 `HeartbeatTests.OnlyWhenIdle_SkipsWhenTraffic`，Tcp 的 `SessionHeartbeat_Fails_Closes`。单独失败时单独重跑该项目确认，并注明。
4. 代码约束沿用 P4 与 P5.1：
   - 异步 API 与 `ConfigureAwait(false)`；
   - 文件作用域命名空间；
   - 英文消息、中文 XML 注释、常量日志模板；
   - 结果判空依赖 P4.5 的可空性标注（不写 `!`）；
   - net472 禁用清单不适用（P6-C1）。
5. CHANGELOG：在 `CHANGELOG.md` 顶部新增一节 `## [Unreleased] — P6.1（Mqtt 1.0.0-preview.1：MQTT 客户端）`，下设 `### 新增（Added）`（需要时再加其他小节）。条目格式为 `- YYYY-MM-DD [Mqtt] 内容`；架构测试的改动记为 `[Architecture]`。
