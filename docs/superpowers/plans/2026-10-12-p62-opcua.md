| P62-D5 | NodeId 用 OPC UA 标准文本，SDK 类型不外露（P6-C4）：<br>• 接受 `i=2258`、`ns=2;s=Line1.Speed`、`ns=2;i=1001`、`ns=1;g=<GUID>`、`ns=1;b=<Base64>`，以及按命名空间 URI 写的 `nsu=<URI>;s=…`（用会话的命名空间表解析，推荐用于配置，因为服务器重启后命名空间索引可能变化）；<br>• 语法错误或 URI 不在命名空间表里时，整个调用返回 `InvalidRequest`（消息写明序号与文本），不发送；<br>• 输出的 NodeId（浏览结果）用 `ns=` 形式；订阅事件里的 NodeId 原样返回调用方传入的文本 | 配置友好；调用方能直接用传入的文本匹配事件 |
| P62-D6 | 值的映射（`Sdk/` 下的一个内部类型，第 17.2 节逐行列出）：<br>• 支持的标量与一维数组映射为 .NET 基本类型；<br>• 不支持的内置类型（结构体 ExtensionObject、多维数组、异构 Variant 数组等）读出时 `Value` 为 null，`UnsupportedType` 给出类型名，状态码照服务器原样返回；<br>• 写入只接受第 17.2 节"写"列中的 .NET 类型，其他类型返回 `InvalidRequest`（序号）；<br>• 写入时不做类型转换，类型必须与节点的数据类型一致（例如 Int16 节点要写 `short`），否则由服务器逐项返回 `BadTypeMismatch` | 用户选择薄类型；结构体留待以后 |
| P62-D7 | 批量语义：<br>• 读、写返回与输入**同序、同长**的逐项结果；<br>• 只有服务级失败（会话断开、超时、服务器拒绝整个请求）才让整个调用失败；<br>• 空列表直接成功，返回空列表，不发请求；<br>• 节点数超过服务器的操作上限（`MaxNodesPerRead`、`MaxNodesPerWrite`、`MaxNodesPerBrowse`）时分批发送后合并。SDK 已经自动分批的，不再实现第二份（Task 0 确认） | 设计 14.2："批量读返回逐项状态码，不压成单个结果" |
| P62-D8 | 便捷方法（扩展方法）：单节点的读、写。逐项状态为 Bad 时返回失败，`ErrorKind` 按第 17.1 节由状态码推出，`ProtocolErrorCode` 为状态码；Uncertain 状态算成功 | 最常见的用法是单点读写 |
| P62-D9 | 浏览：<br>• 正向、层级引用（含子类型），全部节点类别；<br>• 继续点由库处理完（BrowseNext），调用方拿到完整列表；<br>• 每次请求的引用数上限是内部常量，测试经 IVT 调小，用来覆盖继续点路径；<br>• 节点本身的状态为 Bad（如 `BadNodeIdUnknown`）时，整个调用失败，分类同 P62-D8 | 调试与配置工具的常见需求；用户选择纳入 |
| P62-D10 | 订阅：<br>• 每次 `SubscribeAsync` 创建一个 OPC UA 订阅，每个 NodeId 一个监控项（Value 属性，Reporting 模式）；<br>• 处理器作为参数传入，避免"订阅返回之后才挂事件，初始值已经丢了"；<br>• 服务器端创建完成后才返回；超过 `OperationTimeout` 时返回 `Timeout`，并清理已创建的部分；<br>• 每个监控项的创建状态放在 `ItemStatuses`（与 `NodeIds` 同序），部分失败不算整个调用失败；<br>• 通知在 SDK 的回调线程上逐条交付，处理器抛异常只记 Error（`EventSubscribers.InvokeEach`）；<br>• `DisposeAsync` 删除服务器上的订阅（尽力而为，可以重复调用）。断开或释放客户端之后它什么也不做；<br>• 空列表或 NodeId 重复时返回 `InvalidRequest`；<br>• 会话重连后订阅由 SDK 转移或重建，处理器继续收到通知。重建时服务器会重新发送当前值，README 写明 | 用户选择纳入；设计 14.2 |
| P62-D11 | 状态：`OpcUaSessionState { Disconnected, Connecting, Connected, Reconnecting }`，由 SDK 的连接状态映射而来（SDK 的 Closing / Closed 归为 `Disconnected`），经 `StateChanged` 按顺序通知，只在一个地方变化。不是 `Connected` 时，读、写、浏览、订阅一律返回 `NotConnected`，不让 SDK 排队等待 | 设计 14.2：保留原生状态；P6-C11 |
| P62-D12 | 超时：<br>• `ConnectTimeout`：发现端点与创建会话；<br>• `OperationTimeout`：每个服务调用，同时写进请求头的超时提示；<br>• `SessionTimeout`：向服务器申请的会话超时；<br>• `KeepAliveInterval`：会话保活，用来发现断线 | 与已有包的命名一致（毫秒） |
| P62-D13 | 日志：SDK 2.0 自带 `ILogger` 集成（遥测上下文），由 `ILoggerFactory` 构造后交给 SDK（P6-C10）；本库自己的日志按 P6-C10 记录（节点数、耗时，不记录值） | P6-C10 |
| P62-D14 | 依赖注入：`OpcUaClientFactory`（`NamedFactory<OpcUaClient>`）与 `OpcUaServiceCollectionExtensions.AddOpcUaClients()`。名称避开 SDK 自带的 `AddOpcUa()` | P6-C9 |
| P62-D15 | 已知不确定项，写进 README 的"Verification status"：<br>① 只与进程内的官方 Server 联调过，没有对 KEPServerEX、Prosys、西门子、倍福等真实服务器验证；<br>② 只支持 None 安全策略与匿名登录，很多现场服务器默认关闭了 None 策略；<br>③ 2.0 是新版本线；<br>④ 写入不做类型转换 | 诚实记录；② 要在 README 开头醒目说明 |

### 6. Task 2：值类型、选项、NodeId 解析、值映射与错误映射（P62-D5、D6，第 17 节）

**公开 API（固定）**

```csharp
namespace Junevy.Communication.OpcUa;

public enum OpcUaSessionState { Disconnected, Connecting, Connected, Reconnecting }

public enum OpcUaNodeClass
{
    Unspecified = 0, Object = 1, Variable = 2, Method = 4, ObjectType = 8,
    VariableType = 16, ReferenceType = 32, DataType = 64, View = 128,
}

public readonly struct OpcUaStatusCode : IEquatable<OpcUaStatusCode>
{
    public OpcUaStatusCode(uint code);
    public static OpcUaStatusCode Good { get; }
    public uint Code { get; }
    public bool IsGood { get; }            // 最高两位为 00
    public bool IsUncertain { get; }       // 最高两位为 01
    public bool IsBad { get; }             // 最高位为 1
    public string SymbolicName { get; }    // 例如 "BadNodeIdUnknown"；未知码为 "0x80AB0000" 形式
    public override string ToString();     // 例如 "BadNodeIdUnknown (0x80340000)"
    // 相等性成员（Equals、GetHashCode、== 与 !=）按 Code 比较
}

public sealed class OpcUaValue
{
    public object? Value { get; }              // 第 17.2 节的 .NET 类型；状态为 Bad 或类型不支持时为 null
    public OpcUaStatusCode Status { get; }
    public DateTime? SourceTimestamp { get; }  // UTC；服务器没给时为 null
    public DateTime? ServerTimestamp { get; }  // UTC；服务器没给时为 null
    public string? UnsupportedType { get; }    // 不支持的内置类型名；支持时为 null
}

public sealed class OpcUaWriteValue
{
    public OpcUaWriteValue(string nodeId, object value);   // null 抛 ArgumentNullException
    public string NodeId { get; }
    public object Value { get; }
}

public sealed class OpcUaReference
{
    public string NodeId { get; }          // ns= 形式
    public string BrowseName { get; }      // "命名空间索引:名称"，例如 "2:Speed"
    public string DisplayName { get; }
    public OpcUaNodeClass NodeClass { get; }
}

public sealed class OpcUaClientOptions
{
    public string? EndpointUrl { get; set; }                    // 必填，opc.tcp://host:port[/path]
    public string ApplicationName { get; set; } = "Junevy.Communication.OpcUa";
    public string? ApplicationUri { get; set; }                 // null：urn:{机器名}:{ApplicationName}
    public int ConnectTimeout { get; set; } = 10000;            // 毫秒
    public int OperationTimeout { get; set; } = 10000;          // 毫秒
    public int SessionTimeout { get; set; } = 60000;            // 毫秒
    public int KeepAliveInterval { get; set; } = 5000;          // 毫秒
    public int ReconnectInterval { get; set; } = 1000;          // 毫秒
    public int MaxReconnectInterval { get; set; } = 30000;      // 毫秒
}

public sealed class OpcUaSubscriptionOptions
{
    public int PublishingInterval { get; set; } = 1000;         // 毫秒
    public int? SamplingInterval { get; set; }                  // 毫秒；null 表示等于 PublishingInterval
    public uint QueueSize { get; set; } = 1;
    public bool DiscardOldest { get; set; } = true;
}
```

1. 选项校验（`Create` 与 `SubscribeAsync` 时调用）：
   - `EndpointUrl` 必须是绝对的 `opc.tcp` URI；
   - `ApplicationName` 不能为空；
   - 各超时与间隔 > 0，`MaxReconnectInterval` ≥ `ReconnectInterval`；

### 17.1 错误映射（P6-C7，`Sdk/` 下的映射类型）

服务级失败（SDK 抛出的服务异常，或单节点便捷方法、浏览遇到的 Bad 状态）按状态码分类，`ProtocolErrorCode` 为状态码：

| 状态码 | `CommErrorKind` |
|---|---|
| `BadTimeout`、`BadRequestTimeout` | `Timeout` |
| `BadNotConnected`、`BadConnectionClosed`、`BadSecureChannelClosed`、`BadSessionClosed`、`BadSessionIdInvalid`、`BadServerNotConnected`、`BadCommunicationError` | `ConnectionClosed` |
| `BadIdentityTokenInvalid`、`BadIdentityTokenRejected`、`BadUserAccessDenied`、`BadSecurityChecksFailed`、`BadCertificate*` | `AuthenticationFailed` |
| `BadTooManySessions`、`BadTooManyOperations`、`BadTooManySubscriptions`、`BadTooManyMonitoredItems`、`BadOutOfMemory`、`BadResourceUnavailable` | `ResourceExhausted` |
| `BadServiceUnsupported`、`BadNotSupported`、`BadSecurityPolicyRejected`、`BadSecurityModeRejected` | `NotSupported` |
| `BadEncodingError`、`BadDecodingError`、`BadEncodingLimitsExceeded` | `ProtocolViolation` |
| 其他 Bad 状态 | `RemoteError` |

非服务异常：

| 情况 | `CommErrorKind` |
|---|---|
| 调用方的取消令牌触发 | `Cancelled` |
| 连接或操作超时（SDK 的超时异常） | `Timeout` |
| 连接被拒、套接字错误 | `ConnectionClosed` |
| 不是 `Connected` 时调用 | `NotConnected` |
| 服务器没有 None 端点或没有匿名策略（P62-D3） | `NotSupported` |
| NodeId 文本非法、命名空间 URI 未知、写入类型不支持、空列表或重复 NodeId 的订阅 | `InvalidRequest` |
| 释放之后的操作 | `ConnectionClosed` |
| SDK 的其他异常 | `Unspecified` |

逐项结果（读写的每一项、订阅的每个监控项）是**数据**，不是失败；只有 P62-D8 的单节点便捷方法和 P62-D9 的浏览会把 Bad 状态变成失败。

#### 19.2.3 值模型（`exp1`）

`object` 确实被 `Variant`（struct）取代，但"取代"带来一串连带变化：

| OPC UA 内置类型 | `Variant.Value` 的 .NET 类型 |
|---|---|

| Guid | **`Opc.Ua.Uuid`**（struct，`new Uuid(Guid)`，`.Guid` 取回） |
| DateTime | **`Opc.Ua.DateTimeUtc`**（struct，`DateTimeUtc.From(DateTime)`，可隐式转 `DateTime`） |
| ByteString | `Opc.Ua.ByteString` |
| Byte 的数组 | `System.Byte[]` |
| 其余一维数组 | `T[]`（`Uuid[]`、`DateTimeUtc[]`、`ByteString[]` …） |
| LocalizedText / StatusCode / NodeId / QualifiedName / DataValue | 同名 SDK 类型 |
| 多维数组 / `Variant[]` / 结构体 | `int[,]` / `Variant[]` / `ExtensionObject` |

- **公开 API 不变**（第 17.2 节的 `Guid`、`DateTime`），**内部映射要多做两处转换**：`Uuid ⇄ Guid`、`DateTimeUtc ⇄ DateTime`。
- `Variant.From<T>(T)` 的 `T` **必须是 struct**：`Variant.From<object>(42)` 编译不过。所以写入路径必须按 .NET 类型 `switch` 出 `Variant`，不能靠一次装箱转换。
- `VariantHelper.CastFrom / TryCastFrom / CastTo / TryCastTo` 存在，但同样是泛型 struct 约束。
- **`byte[]` 与 ByteString 的歧义是真的**：同一个 `byte[]` .NET 值写进 ByteString 节点按 ByteString 解释、写进 Byte 数组节点按 Byte 数组解释，只能靠节点数据类型区分（与第 17.2 节的说明一致）。

#### 19.2.4 NodeId 与命名空间（`exp1` / `exp4`）

| 文本 | `NodeId.Parse` | `NodeId.ParseLongForm(text, NamespaceTable)` |
|---|---|---|
| `i=2258` | OK `ns=0;i=2258` | OK |
| `ns=2;s=Line1.Speed` | OK | OK |
| `ns=2;i=1001` / `ns=1;g=<GUID>` / `ns=1;b=<Base64>` | OK | OK |
| `s=Line1.Speed` / `b=AQI=` | OK（ns 0） | OK |
| `nsu=urn:junevy:opcua:test;s=Counter` | **`ArgumentException: InvalidNamespaceUri`** | **OK → `ns=1;s=Counter`** |
| `nsu=<未知 URI>;s=X` | `ArgumentException` | **`ServiceResultException` + `NodeIdParseError.NoNamespaceMapping`** |
| `ns=;s=x` / `ns=abc;s=x` / `i=notanumber` | `ServiceResultException`（`InvalidNamespaceIndex` / `InvalidIdentifier`） | 同 |
| `""`（空串） | **OK，解析成 `i=0`** | 同 |

- `nsu=` **只能走 `NodeId.ParseLongForm`**（或 `NodeId.Create(identifier, uri, table)`）。命名空间表 API：`NamespaceTable.Count`、`GetString(ushort)`、`GetIndex(string)`、`ToArray()`。
- 两类异常（`ArgumentException` 与 `ServiceResultException`）都要映射成 `InvalidRequest`。
- **空串会被解析成 `i=0`**，本库必须自己拒绝（P62-D5 的"语法错误"包含空串）。

#### 19.2.5 状态码（`exp1`）

- `StatusCode.LookupSymbolicId(uint)`：`0x00000000` → `"Good"`、`0x40000000` → `"Uncertain"`、`0x80340000` → `"BadNodeIdUnknown"`、**未知码 → 空串**（不是 `null`，也不是 `0x…` 形式）。
- **子码被忽略**：`0x00000001` → `"Good"`、`0x00000002` → `"Good"`。P62 第 6 节 `SymbolicName` 的"未知码为 `0x80AB0000` 形式"由本库自己生成（空串时回退），并且**例子里的 `0x80AB0000` 其实是有名字的**（`BadInvalidArgument`），README/测试不要用它当未知码。
- **SDK 的 `StatusCode.IsUncertain(0xC0000000)` 为 `true`，同时 `IsBad(0xC0000000)` 也为 `true`**。本库按 P62 第 6 节自己从最高位算，不复用 SDK 的判定，避免把这个差异带进公开类型。

#### 19.2.6 客户端会话（无 DI，`exp5` / `exp7`）

可用（关键是入口）：

```csharp
var instance = new ApplicationInstance(telemetry) { ApplicationName = …, ApplicationType = ApplicationType.Client, ConfigurationType = typeof(ApplicationConfiguration) };
var config = await instance.Build(applicationUri, productUri).AsClient()
        .AddSecurityConfiguration(subjectName, pkiRoot, appRoot, rejectedRoot)
            .SetAutoAcceptUntrustedCertificates(true).SetRejectSHA1SignedCertificates(false)
    .CreateAsync(ct);

var session = await new ManagedSessionBuilder(config, telemetry)
    .UseEndpoint(endpointUrl, MessageSecurityMode.None, SecurityPolicies.None)
    .WithUserIdentity(new UserIdentity())
    .WithSessionTimeout(TimeSpan.FromSeconds(60))
    .WithReconnectPolicy(o => new ReconnectPolicyOptions { InitialDelay = …, MaxDelay = …, JitterFactor = 0.2, MaxRetries = -1, Strategy = BackoffStrategy.Exponential })
    .WithTransferSubscriptionsOnRecreate(true)
    .ConnectAsync(ct);
```

- `UseEndpoint(url, mode, policy)` 内部自己发现端点，**不需要**手动 `CoreClientUtils.SelectEndpoint`。
- **`ConnectAsync` 没有超时参数**，见摩擦 F2。

#### 19.2.7 否定用例（`exp7`，每条一个进程）

| 场景 | 观测到的行为 |
|---|---|
| 端口无监听 | `ConnectAsync` **一直阻塞**，直到调用方的令牌触发 → `TaskCanceledException` |
| 只开放加密端点（`IncludeUnsecurePolicyNone=false`、`IncludeSignAndEncryptPolicies=true`） | 同样阻塞到令牌触发，**拿不到任何状态码** |
| 不允许匿名（只有 `UserTokenType.UserName`） | 同样阻塞到令牌触发；服务器日志只有一条 "User token policy UserName is configured without a matching identity authenticator." |
| 端点里报告 `opc.tcp://opcua-test.invalid:<port>/UA/`（不可解析），客户端用 `127.0.0.1` | **连接成功**，`session.Endpoint.EndpointUrl` 是配置里的 `opc.tcp://127.0.0.1:<port>/UA/` → **P62-D3 ④ 由 SDK 免费提供**（`UseEndpoint(url, …)` 生效） |
| 服务器停止后 `ReadAsync` | 抛 `ServiceResultException`，`StatusCode = BadConnectionClosed`，**不是**逐项状态码 |
| 服务器停止后 | `ConnectionStateChanged` 事件**每次重试都触发**（不合并），`ReconnectAttempt` 递增 |

**对设计的影响**：P62-D3 的 ② 与 ③（没有 None 端点 / 没有匿名 → `NotSupported`）**必须由本库在发现端点后自己判定**，不能指望 SDK 报告；`ConnectTimeout`（P62-D12）**必须由本库开 `CancellationTokenSource`**；P62-D11"只在一个地方变化"意味着要过滤 SDK 事件里的重复状态。

#### 19.2.8 批量与浏览（P62-D7、P62-D9，`exp5`）

- 服务器上报的操作上限在客户端可见：`session.OperationLimits.{MaxNodesPerRead, MaxNodesPerWrite, MaxNodesPerBrowse}`（实测 `5 / 5 / 2`）。
- **`MaxNodesPerRead = 5` 时，一次 `ReadAsync` 读 12 个节点返回 12 个正确结果、`serviceResult = Good`（没有 `BadTooManyOperations`，也没有异常）→ SDK 自动分批。** 计划"P62-D7：SDK 已经自动分批的，不再实现第二份"成立。
- 浏览：`BrowseAsync(requestHeader, view, requestedMaxReferencesPerNode, nodesToBrowse, ct)`。
  - `requestedMaxReferencesPerNode = 0`（"服务器默认"）时一次返回全部 38 条引用、**没有继续点**；
  - 传 `2` 时 19 轮、每轮一个继续点 → **必须由本库传自己的上限**才能走继续点路径；
  - `BrowseNextAsync(requestHeader, releaseContinuationPoints, ArrayOf<ByteString>, ct)`，**`BrowseDescription` 在 2.0 里没有 `ContinuationPoint` 成员**；
  - 浏览不存在的节点 → `BrowseResult.StatusCode = BadNodeIdUnknown`（**逐节点**，不是服务级异常）。
- 写：`WriteAsync(requestHeader, ArrayOf<WriteValue>, ct)` → `WriteResponse.Results` 是 `ArrayOf<StatusCode>`，逐项。

#### 19.2.9 订阅（V2，`exp5`）

- `session.AddSubscription(handler, SubscriptionOptions | Func<SubscriptionOptions, SubscriptionOptions>)` → `Opc.Ua.Client.Subscriptions.ISubscription`。
- 添加监控项：`subscription.MonitoredItems.TryAdd(name, IOptionsMonitor<MonitoredItemOptions>, out IMonitoredItem)`；不想构造 `IOptionsMonitor` 时用扩展 `ManagedSessionExtensions.TryAddMonitoredItem(subscription, name, MonitoredItemOptions, out IMonitoredItem)`。
- **监控项的创建是异步的**：`TryAdd` 返回后 `IMonitoredItem.Created` 仍是 `false`，要轮询。
- **逐项状态确实分开**：一个不存在的节点 → 该项 `Created == false`、`Error = BadNodeIdUnknown`，而订阅本身 `Created == true`、其余项照常。→ P62-D10 的 `ItemStatuses` 有 SDK 原生支持。
- 回调：`ISubscriptionNotificationHandler.OnDataChangeNotificationAsync(ISubscription, uint, DateTime, ReadOnlyMemory<DataValueChange>, PublishState, IReadOnlyList<string>)`，返回 `ValueTask`，在 SDK 的线程上；`DataValueChange` 带 `IMonitoredItem` 与 `DataValue`。

#### 19.2.10 遥测与日志（P62-D13）

- 入口就是 `DefaultTelemetry.Create(Action<ILoggingBuilder> configure)` → `ITelemetryContext`。**没有** `new HostTelemetryFactory(loggerFactory)` 这种类型；`ILoggerFactory` 通过 `ILoggingBuilder` 进来。
- 服务端侧另有 `Opc.Ua.Server.Hosting.HostTelemetryContext(ILoggerFactory)`（只给测试服务器用）。

#### 19.2.11 重连与状态（P62-D2、P62-D11，`exp7`）

- `Opc.Ua.Client.ConnectionState { Disconnected=0, Connecting=1, Connected=2, Reconnecting=3, Failover=4, Closing=5, Closed=6 }` —— 与 P62-D11 的 `OpcUaSessionState` 几乎一一对应（多出 `Failover`；`Closing`/`Closed` 按计划归入 `Disconnected`）。
- `ConnectionStateChangedEventArgs { PreviousState, NewState, Error(ServiceResult), ReconnectAttempt, UnderlyingChannelState }`。
- `ChannelState { Disconnected, TransportConnecting, TransportReconnecting, TransportConnectedSessionReactivating, Ready, Faulted, Closed }`。
- `ReconnectPolicyOptions` 的属性是 **init-only**，必须 `new ReconnectPolicyOptions { … }`；`MaxRetries = -1` 表示不限次数；`Strategy` 是 `BackoffStrategy`。

#### 19.2.12 测试服务器（`exp5`）

- **托管方式是通用宿主**，不是 `StandardServer` 直调：

```csharp
var host = new HostApplicationBuilder();
host.Services.AddSingleton(telemetry);
host.Services.AddOpcUa().AddOpcTcpTransport()
    .AddServer(o => { … })
    .AddNodeManager("urn:junevy:opcua:test", buildAddressSpace);
await host.Build().StartAsync();     // 由 OpcUaServerHostedService 启动
```

  `provider.GetRequiredService<IOpcUaServerFactory>().CreateServer(...)` 只创建，不监听；`StandardServer.StartAsync(ApplicationConfiguration, CancellationToken)` 需要自己准备 `ApplicationConfiguration`，而 DI 路径不会把它注册进容器。
- `OpcUaServerOptions.OperationLimits` **默认是 null**，直接赋值会 NRE；要用 `o.ConfigureBuilder = b => b.SetOperationLimits(new OperationLimits { … })`。
- 地址空间：`b.AddFolder("Test", ObjectIds.ObjectsFolder)`、`b.AddVariable<T>("Int32", parentNodeId)` + `RuntimeValueBuilderExtensions.Bind(variable, out IValueUpdater<T> updater)` → `updater.SetValue(value)`。
  - **只写 `OnRead` 不够**：服务器一直回 `BadWaitingForInitialData`，必须 `Bind` + `SetValue`。
  - **必须 `AccessLevelBuilderExtensions.Writable(node, true)`**，否则写回来是 `BadNotWritable`（只读变量则正是我们想要的）。
- NodeId：默认 `IRebasableNodeIdFactory` 给的是**数字** NodeId（`ns=2;i=…`）。`WithNodeIdAssignment(NodeIdAssignmentMode.String)` 给的是规范路径串（`ns=2;s=v1:0::8:l:4:Test`）。**自定义 `IRebasableNodeIdFactory`（按浏览名返回 `s=<name>`）会让服务器起不来**（`BadNodeIdInvalid 'Unexpected error starting application'`）→ 测试服务器保留默认数字 NodeId，建地址空间时把 `NodeId` 记下来。
- 取回已分配 NodeId：建完节点后 `b.Node("Test/Int32").Node.NodeId`（浏览路径，`/` 分隔，相对命名空间根而不是 ObjectsFolder）。**嵌套文件夹下的路径不能从根解析**（`Sub/Leaf` 失败），要用 `b.Node(subNodeId).Child(browseName)`；`INodeBuilder.Child(name)` 是**查找**，不存在时抛异常。
- 证书目录：服务器首次启动会生成证书，耗时长；每次运行用唯一临时目录、结束删除即可（与计划第 1 节第 4 条一致）。

#### 19.2.14 与计划假设不同的地方（里程碑 1 小结要求）

1. **P62-D4 结论修正**：SDK **不要求** `None` 策略下有客户端证书。`ApplicationInstance.DisableCertificateAutoCreation = true` 时，`AddSecurityConfiguration(...)` 之后 `pki` 目录里**一个文件都没有**（`ApplicationCertificates.Count` 仍是 1，但那只是配置）。不过 `AddSecurityConfiguration(subjectName, pkiRoot, appRoot, rejectedRoot)` 本身是 `AsClient()` 之后**必需的一步**，所以 **`PkiRoot` 选项照旧保留**（默认 `%LocalAppData%\Junevy.Communication\OpcUa\pki`），只是**不会**为本库生成自签名证书。仍然是本期唯一预先批准的公开 API 变动。
2. **P62-D3 ②③ 的实现位置改变**：必须由本库判定，不是等 SDK 报错（见 19.2.7）。
